faq:
  - q: 既然已经开启了系统代理，为什么终端命令行和部分桌面游戏还是不走代理，必须开 TUN 模式？
    a: 因为系统代理本质上只是向操作系统登记了一个本地代理端口建议，只有 Chrome、Edge、Safari 等主动读取系统设置的软件才会遵守；终端里的 git、curl、docker、部分桌面应用、UWP 程序以及 UDP 游戏联机默认完全无视系统代理。TUN 模式则是在系统网络层创建虚拟网卡直接拦截三层数据包，实现全设备无死角接管。
  - q: 为什么在 Clash Verge Rev 里打开了 TUN 开关，但命令行和游戏依然走直连没有任何效果？
    a: 创建虚拟网卡并改写操作系统路由表属于高权限内核调用，普通用户权限无法生效。在 Windows 上必须先安装并启动 Service Mode 服务模式，在 macOS 上需要通过密码授权安装辅助服务或开启网络扩展，Linux 则需赋予核心 CAP_NET_ADMIN 能力。仅点亮界面开关而底层服务未运行时，流量并不会进入虚拟网卡。
  - q: 什么是路由环路（Routing Loop），为什么开启 TUN 后有时会瞬间全网断流、CPU 飙升？
    a: 路由环路是指代理内核自己向机场服务器节点发起连接时，数据包没有直接走物理网卡出去，反而又被自己创建的 TUN 虚拟网卡截获并重新送回自己，形成无限死循环。常见诱因包括关闭了 auto-detect-interface 自动出站网卡识别、电脑同时运行两款代理软件的 TUN 网卡，或将上游 DNS 配成了会被自身再次拦截的环路地址。
  - q: 开启 TUN 模式或关闭 TUN 模式后突然整个电脑彻底断网（连国内网站也打不开），如何安全回滚？
    a: 请立即按顺序执行四步回滚：首先在客户端关闭 TUN 开关与系统代理开关并彻底退出软件；其次检查并停止 Service Mode 服务或禁用残留虚拟网卡；接着打开物理网卡设置确认 IPv4 的 IP 与 DNS 已恢复为自动获取（DHCP）；最后在终端刷新系统 DNS 缓存即可迅速恢复直连。严禁以关闭杀毒软件或删除系统注册表方式排障。
  - q: 家里已经部署了 OpenWrt 软路由透明代理，电脑或手机上还需要开启 TUN 模式吗？
    a: 不需要，而且严禁同时开启。当主路由或旁路由已经通过 OpenClash、PassWall2、Nikki 或 HomeProxy 接管全屋设备流量时，单机再开 TUN 模式会形成代理套代理的双层加密环路与 Fake-IP 二次解析死锁，导致网页卡死或网速暴跌。连接软路由网络时应彻底关闭本机代理客户端。
  - q: Windows 开启 TUN 模式后导致 WSL2 或 Hyper-V 虚拟机无法上网怎么办？
    a: 这是因为 WSL2 与虚拟机通过虚拟交换机与宿主机通信，开启 TUN 并配合 strict-route 时可能截断或混淆子网回包路由。常见解决方法是确保局域网与 WSL 私有网段已加入路由排除（route-exclude-address），并开启 allow-lan 与正确的网卡栈兼容设置，避免宿主机默认路由强行吞掉虚拟机桥接流量。
  - q: 如果平时只是偶尔在终端里用一下 git 或 curl，不想长期开启高风险的 TUN 模式有什么替代方案？
    a: 可以通过在终端会话中临时设置 HTTP_PROXY 和 HTTPS_PROXY 环境变量指向客户端的本地混合端口（例如 127.0.0.1:7897），用完关闭终端窗口即自动失效。这种低风险方案无需安装虚拟网卡驱动、不会改写全机路由表，也不会与企业 VPN 或虚拟机产生冲突。

# TUN 模式教程：虚拟网卡原理、全平台权限授权与路由环路回滚

> **核心结论（Answer-First）**：**TUN 模式**通过在操作系统内核网络层创建一张虚拟网卡（如 `Meta`、`wintun`、`utun` 或 `sing-tun`）并改写系统路由表，把本机所有软件发出的 TCP 与 UDP 三层数据包统一接管进代理内核处理，从而彻底解决“系统代理管不到终端命令行、部分桌面端、UWP 应用与 UDP 游戏”的难题。但正因为 TUN 涉及 **虚拟网卡驱动加载、高权限服务授权与系统路由表及 DNS 劫持**，属于 **高风险底层网络操作**——日常仅浏览网页时优先使用低风险的「系统代理」，确需全链路接管时再严格按平台授权规范开启，并事先掌握断网回滚步骤。

如尚未熟悉基本策略组与模式切换，可先阅读 [Clash 配置教程](/guides/clash-setup/)；若已明确了解原理、需要排查具体故障，可直达 [TUN 开启无效与虚拟网卡冲突排查](/troubleshooting/articles/tun-not-working)。

## 一、TUN 虚拟网卡工作原理与核心网络栈解析

要理解为什么开系统代理时浏览器能上外网、终端敲 `git clone` 却依然超时，必须看清两者工作在 OSI 网络模型完全不同的层级上。

### 1. 数据包接管路径与网络栈（Stack）选择
开启 TUN 后，客户端干了三件事：
1. 调用系统虚拟网卡驱动创建一张虚拟接口，并分配私有/保留网段地址（如 `198.18.0.1` 或 `172.19.x.x`）。
2. 向操作系统的路由表写入高优先级默认路由（通常覆盖 `0.0.0.0/1` 与 `128.0.0.0/1` 或通过接口跃点数抢占默认出口），使几乎所有出站流量自动流向该虚拟网卡。
3. 代理核心从虚拟网卡读取原始 IP 数据包，结合 Fake-IP 或嗅探（Sniffing）还原出目标域名和端口，匹配 [分流规则](/guides/split-routing/) 后，决定走物理网卡直连还是经加密隧道发往机场节点。

在 Mihomo 与 sing-box 内核配置中，常见的 `stack`（用户态协议栈）分为三种：
- **`system`（系统栈）**：直接借助操作系统原生网络栈处理 TCP/UDP，大吞吐下 CPU 占用最低、峰值速度最高，但在部分老旧 Windows 系统或极端网络环境中偶发兼容性问题。
- **`gvisor`（用户态协议栈）**：完全由内核内置的网络栈代码在用户态重组数据包，对各类复杂容器、虚拟机或非标准系统环境兼容性极好，缺点是万兆级别高吞吐时 CPU 占用略高。
- **`mixed`（混合栈，现代默认推荐）**：TCP 流量走高性能 `system` 栈，UDP 流量走兼容性稳定的 `gvisor` 栈，兼顾日常网页速度与游戏/语音 UDP 稳定性。

### 2. MTU 参数对大包卡死的影响
虚拟网卡默认的 MTU 通常在 `1500` 或 `9000`（部分客户端预设）。如果在某些宽带 PPPoE 拨号、校园网或多层隧道环境下发现“小文字消息能通、一传大文件或开 SSH/网页图片就卡死”，往往是数据包分片失败所致，将 TUN 的 MTU 适度调低至 `1400` 或 `1280` 往往能立竿见影消除分片丢包。

## 二、系统代理（System Proxy）vs TUN 模式深度对比与低风险替代

很多教程不问需求就教新手上来直接开 TUN，这其实把大量无需承担驱动风险的用户推向了高故障率。请先对照下表判断你到底需不需要开 TUN：

| 对比维度 | 系统代理（System Proxy） | TUN 模式（虚拟网卡接管） |
| :--- | :--- | :--- |
| **工作层级** | 应用层环境变量与系统 HTTP/SOCKS 端口登记（如 `127.0.0.1:7897`） | 操作系统三层网络接口（虚拟网卡驱动 + 系统路由表） |
| **接管范围** | 仅限遵守系统代理的浏览器与部分桌面程序 | **几乎全设备所有进程**（终端 CLI、`docker`、IDE 插件、UWP、部分游戏与 UDP） |
| **系统权限要求** | 普通用户权限即可一键开关 | Windows 需安装 Service Mode；macOS 需 Helper/系统扩展；Linux 需 `CAP_NET_ADMIN` |
| **常见副作用** | 异常退出未清注册表时残留死端口，关闭系统代理即可恢复 | 多虚拟网卡路由冲突、企业 VPN 断连、WSL2/AirDrop 异常、**断网回滚步骤更复杂** |
| **适用推荐级别** | **日常浏览器上网与办公的默认首选（低风险）** | **仅当系统代理明确管不到的工具需要出海时按需开启** |

### 不想开 TUN 时，终端命令行的零风险替代法
如果你平时只在浏览器上网，只是偶尔需要在 Windows PowerShell 或 macOS/Linux Terminal 里执行一次 `git clone`、`pip` 或 `curl`，完全不需要动用虚拟网卡——只需在当前终端窗口临时注入代理环境变量（假设本地客户端混合端口为 `7897`）：

```powershell
# OS: Windows (PowerShell)
# 目的: 仅对当前这一个终端窗口临时走本地代理端口，关闭窗口自动失效（零驱动、零路由修改）
# 风险: 无系统级修改风险
$env:HTTP_PROXY="http://127.0.0.1:7897"
$env:HTTPS_PROXY="http://127.0.0.1:7897"
```

```bash
# OS: macOS / Linux (Terminal)
# 目的: 仅对当前 shell 会话临时设置终端代理环境变量
# 风险: 只作用于当前会话，输入 unset 即可秒撤回
export http_proxy="http://127.0.0.1:7897"
export https_proxy="http://127.0.0.1:7897"
```
**输出解读**：执行后当前终端内的 `git`、`curl`、`npm` 就会立即走客户端代理通道；排障或下载结束后直接关掉终端，或执行 `unset http_proxy https_proxy`，本机网络零残留。详细差异延伸阅读：[TUN 模式与系统代理区别](/troubleshooting/articles/tun-vs-system-proxy)。

## 三、Windows / macOS / Linux 全平台权限授权与共存排雷

为什么点亮了界面里的 TUN 开关却毫无反应？答案几乎全在 **「底层权限授权」** 与 **「多网卡冲突」** 上。

### 1. Windows 端：Service Mode（服务模式）与 WSL2 共存
- **必须安装 Service Mode**：以 **[Clash Verge Rev](/clients/clash-verge/)** 为例，普通双击运行属于标准用户权限，无法创建 Wintun 虚拟网卡。必须进入客户端 `设置 -> Clash 设置 / 系统设置 -> 服务模式 (Service Mode)` 点击安装服务，弹出 UAC 确认后等待图标变成绿色激活状态，再重启核心并开启 TUN 开关。
- **不要同时混开“系统代理”与“TUN”**：在现代客户端中，一旦稳定开启 TUN，系统会自动将流量从网卡层接管，此时一般建议关闭“系统代理”开关，避免部分应用同时读取应用层代理端口又被底层网卡二次处理造成端口损耗或异常日志。
- **多虚拟网卡共存禁忌**：若电脑上同时安装了 **企业零信任 VPN（如 EasyConnect）、其他游戏加速器、Tailscale 或未卸载干净的旧版 Clash for Windows 服务**，多张虚拟网卡会同时向系统路由表争夺最高优先级，极易导致全网断流。**同一时间只能保留一套网络接管程序处于活跃状态**。
- **WSL2 / Hyper-V 虚拟机开启 TUN 后无法上网修复**：开启 TUN（尤其配合 `strict-route: true`）后，Windows 宿主机可能截断 WSL2 虚拟交换机子网（常见 `172.16.0.0/12` 或 `192.168.x.x`）的回包或导致 DNS 无法穿透。排查时需确认客户端已开启 `allow-lan: true` 以便接收来自 WSL 子网的请求，并在 `route-exclude-address` 中排除虚拟机内部网段，同时检查 Windows 防火墙是否放行了虚拟交换机向宿主机代理端口的入站流量（切记：仅配置针对 WSL 接口或应用的放行规则，**严禁直接彻底关闭 Windows 防火墙或杀毒软件**）。

### 2. macOS 端：系统扩展授权、`utunX` 与 AirDrop 局域网兼容
- **Helper / 网络扩展授权**：macOS 开启 TUN 需要输入管理员开机密码安装辅助进程，或在 `系统设置 -> 隐私与安全性 / 网络 -> VPN 与过滤器` 中允许应用加载系统网络扩展。成功激活后，系统底层会新建一张名为 `utun3`、`utun4` 等编号的虚拟网络接口。
- **Apple Silicon 芯片务必装原生包**：使用 M1/M2/M3/M4 系列 Mac 时，切勿运行 Intel 转译版客户端来拉起虚拟网卡守护进程，请按 [客户端安装教程](/guides/installation/) 下载原生 `arm64` 安装包。
- **AirDrop 隔空投送、连续互通与 Time Machine 中断排查**：部分激进的 TUN 配置如果把全部本地多播段（如 `224.0.0.0/4`）或局域网私有段强行吞进虚拟网卡，会导致隔空投送找不到设备或 NAS 备份中断。务必核对配置开启了本地局域网排除（`route-exclude-address` 包含局域网私有段），并在客户端内置规则最顶部保留局域网 `DIRECT`。

### 3. Linux 端：`CAP_NET_ADMIN` 能力与 systemd 服务
- Linux 桌面或无头环境要让普通用户进程创建 `/dev/net/tun` 并配置路由，有两种规范方式：一是通过安装包自带的 systemd 系统服务以受控特权守护进程运行核心；二是仅为内核二进制文件授予最小必要的网络管理能力（`CAP_NET_ADMIN` 和 `CAP_NET_BIND_SERVICE`），而不是直接以 root 身份长期运行整个图形界面。同时确认系统已加载 `tun` 内核模块。

## 四、致命故障预防：路由环路（Routing Loop）与防环路参数

如果开启 TUN 的瞬间，软件日志疯狂刷屏报错、电脑风扇狂转、CPU 占用飙高到 50% 以上且全网彻底断流，十有八九触发了 **路由环路（Routing Loop）**。

### 路由环路的形成机理
1. 代理核心需要将加密流量发往远端机场服务器 IP（例如 `203.0.113.10`）。
2. 当操作系统的默认路由已经被 TUN 改写为“所有流量都进 TUN 网卡”时，如果代理核心忘记告诉操作系统 **“我自己发往物理网卡的包不要再进 TUN”**，或者它绑定错了物理网卡（例如电脑刚从网线拔掉切换到了 Wi-Fi），那么核心发给机场节点的数据包就会被本机自己的 TUN 网卡截获，再交回核心自己处理，无限循环直到耗尽句柄与系统资源。

### 预防路由环路的三大关键防线
1. **必须保持 `auto-route: true` 与 `auto-detect-interface: true`**：
   这两个参数是 Mihomo / sing-box 防止自我循环的生命线。`auto-detect-interface: true` 会自动探测当前真正连接外网的物理网卡（如 `WLAN` 或 `en0`）并自动将代理核心自己的出站流量绑定到该物理接口绕过 TUN。切勿在不懂原理的情况下将其改为 `false` 或写死一个已经不存在的网卡名。
2. **明确配置 `dns` 的节点入口解析器**：
   用于解析机场节点域名的 `proxy-server-nameserver` 必须直连解析（详见 [DNS 与 Fake-IP 配置指南](/guides/dns-setup/)），绝不能依赖 TUN 拦截后的自身节点去解析节点域名本身。
3. **禁止“软路由透明代理 + 单机 TUN”双层套娃**：
   当家里的 OpenWrt 软路由已经跑着 OpenClash / PassWall2 / Nikki / HomeProxy 透明代理时，连在局域网内的电脑手机千万别同时开 TUN，否则双层 TUN 与双层 Fake-IP 会立刻引发卡死与环路。

## 五、只读终端检查命令（核对虚拟网卡、接口状态与路由表）

在怀疑 TUN 未生效、或者准备回滚却不知道系统里到底残留了哪张虚拟网卡时，先用以下 **只读查询命令** 摸清现场状态（绝不修改任何参数）：

### Windows（PowerShell，只读查询）
```powershell
# OS: Windows 10 / 11 (PowerShell)
# 目的: 列出当前所有网络适配器状态与名称，排查是否存在多张 VPN/TAP/TUN 虚拟网卡冲突
# 风险: 纯只读查询，零修改风险
Get-NetAdapter | Select-Object Name, InterfaceDescription, Status, LinkSpeed
```
```powershell
# OS: Windows 10 / 11 (PowerShell)
# 目的: 查看当前系统 IPv4 路由表中的默认网关（0.0.0.0/0）跃点数权重，判断流量优先走向物理网卡还是虚拟网卡
# 风险: 纯只读查询，零修改风险
Get-NetRoute -DestinationPrefix "0.0.0.0/0" -AddressFamily IPv4 | Select-Object InterfaceAlias, NextHop, RouteMetric, InterfaceMetric
```
**输出解读**：在 `Get-NetAdapter` 中，正常单机开 TUN 时除物理网卡（如 `Wi-Fi`、`以太网`）外，应仅有一张活跃的 `Meta`、`sing-tun` 或 `Wintun` 接口处于 `Up` 状态；如果同时出现企业 VPN、其他加速器多张虚拟网卡均显示 `Up`，就是明确的多网卡争抢冲突。若在客户端已经退出后依然看到代理虚拟网卡滞留且 `Status` 为 `Up`，则需要按第六节回滚停用服务。

### macOS / Linux（Terminal，只读查询）
```bash
# OS: macOS / Linux (Terminal)
# 目的: 查看活跃的 utun / tun 虚拟接口及其分配的内网地址（如 198.18.0.1 或 172.19.x.x）
# 风险: 纯只读查询，无更改风险
ip addr show 2>/dev/null || ifconfig | grep -E "^(utun|tun|en|wlan)[0-9]" -A 4
```
**输出解读**：开启 TUN 正常时，列表里会出现带着 `UP,POINTOPOINT,RUNNING` 标志且绑定了 `198.18.0.1` 或 `172.19.0.1` 的 `tun0` / `utunX` 接口；若根本没有相关接口，说明权限不足（未装 Helper 或缺 `CAP_NET_ADMIN`），虚拟网卡根本没拉起来。

### 全平台 TUN 异常定位与参数调优对照矩阵

| 常见 TUN 异常现象 | 最可能的核心诱因 | 低风险只读核查动作 | 对应修正与处置方向 |
| :--- | :--- | :--- | :--- |
| **点亮 TUN 开关后，浏览器正常但终端 `git` / `curl` 仍直连超时** | 未安装或未启动 Windows Service Mode / macOS Helper；或仍存在旧客户端竞争端口 | Windows 运行 `Get-NetAdapter` 看虚拟网卡是否存在且为 `Up`；macOS 看是否生成新 `utunX` | 安装并启动绿色的系统服务模式（Service Mode）或授权网络扩展，重启核心后再测试 |
| **开启 TUN 瞬间系统风扇狂转、CPU 占用飙高且全部网络中断** | 触发了 **路由环路**：核心自己的外连流量没有绕过 TUN 虚拟网卡，形成自我死循环 | 检查日志文件是否疯狂刷出大量重复连接记录或 `too many open files` | 确保配置中 `auto-route: true` 与 `auto-detect-interface: true` 均已开启，并核对节点解析直连 |
| **能正常发文字或连网页，但 SSH 会话与大文件传输经常卡死断流** | TUN 虚拟网卡 `MTU` 值与物理宽带或叠加隧道不匹配导致数据包分片丢包 | 检查客户端 TUN 高级参数中的 `mtu` 数值（例如部分预设过高设为 `9000`） | 将 TUN `mtu` 调整为标准 `1500` 或更稳妥的 `1400` / `1280` 后重启核心验证 |
| **家里插着企业零信任 VPN 或游戏加速器，开 TUN 后双方一起掉线** | 多张虚拟网卡同时改写默认网关与路由跃点数，导致流量不知该进哪张虚拟接口 | 执行 `Get-NetRoute -DestinationPrefix "0.0.0.0/0"` 查看哪张接口排在最高权重 | **严禁多虚拟网卡同时工作**：使用办公 VPN 或游戏加速器时先关掉代理 TUN，按场景错峰切换 |
| **Windows 开启 TUN 后 WSL2 子系统或 Docker 容器完全断网** | `strict-route` 接管过严拦截了虚拟交换机回包，或未开启 `allow-lan` 接收子网请求 | 在 WSL2 内执行只读探测确认是否仅 DNS 超时或整段路由不可达 | 开启 `allow-lan: true`，在 `route-exclude-address` 中排除 WSL 虚拟网段，仅在防火墙放行该子网交互 |
| **macOS 开启 TUN 后 AirDrop 隔空投送找不到旁边 iPhone** | 激进路由配置把本地组播段或局域网发现流量强行吸入了 `utun` 隧道 | 核对 TUN 配置中的局域网路由排除项与规则顶部直连列表 | 确保 `route-exclude-address` 包含私有与本地链路网段（如 `169.254.0.0/16` 与内网段） |

### 彻底停用或清理损坏的 Wintun / Mihomo 虚拟网卡规范步骤
若客户端曾非正常崩溃导致每次启动 TUN 都报错 `create tun failed` 或虚拟适配器处于卡死异常状态，切忌使用第三方未知“注册表清理工具”，按以下安全流程重置适配器即可：
1. 在客户端界面关闭 TUN 模式后，先进入「设置 -> 服务模式」点击卸载/停用 Service Mode 并彻底退出客户端。
2. Windows 右键开始菜单打开 **「设备管理器」 -> 展开「网络适配器」**，查看是否存在遗留的感叹号 `Wintun`、`Meta` 或已卸载旧版 `Clash` 虚拟网卡设备；如有旧版停更软件残留的虚拟设备，右键卸载该虚拟设备（注意千万不要误删真实的 Intel/Realtek 无线或有线物理网卡），重启电脑后再重新打开新版官方客户端安装服务模式即可自动重建健康虚拟网卡。

### 进阶专题延伸规划（持续深入方向）
在熟悉 TUN 虚拟网卡日常启用与安全回滚后，站内后续可按以下细分场景继续深化底层调优：
- **协议栈吞吐对比**：深入验证 `system`、`gvisor` 与 `mixed` 三类 TUN 协议栈在千兆宽带下的 CPU 开销与 UDP 丢包率。
- **精细路由参数**：掌握 `auto-route`、`auto-detect-interface` 与 `strict-route` 在多网卡笔记本（有线/Wi-Fi 自动切换）环境中的防环路边界。
- **局部终端环境变量替代**：系统梳理在不开虚拟网卡的前提下，仅通过 `HTTP_PROXY` 覆盖特定命令行工具的零风险日常工作流。

## 六、高风险警示与关闭 TUN 后断网标准回滚步骤

> [!CAUTION]
> **高风险操作警告**：
> 1. **严禁通过关闭 Windows Defender、macOS 防火墙或第三方杀毒软件来尝试“修复”TUN 虚拟网卡报错**。
> 2. 在进行线上视频会议、远程桌面（RDP/SSH）或银行大额转账期间，**切勿突然切换 TUN 开关**，路由表重置瞬间会导致所有现有长连接断线。
> 3. 出现全网断网时，切忌上网乱搜脚本强删注册表 `NetworkList` 或随意运行来历不明的所谓“一键网络重置批处理”。

**无论是在开启 TUN 时发生环路断网，还是关闭 TUN 退出客户端后发现电脑依然彻底上不了国内网页，请严格按以下 5 步安全回滚：**

1. **第一时间软关闭 TUN 与系统代理并退出客户端**：
   - 打开代理客户端界面，依次关闭 **「TUN 模式」** 开关与 **「系统代理」** 开关，等待 5 秒后彻底退出软件（右键系统托盘图标选择退出，而非仅点右上角叉号最小化）。
2. **停止并卸载后台服务模式（Windows / macOS）**：
   - 若退出软件后全网依然断流，重新打开客户端进入设置页，找到 **「Service Mode / 服务模式」** 点击 **停止 / 卸载服务**，确保系统进程列表里不再残留 `mihomo`、`clash-meta` 或 `sing-box` 后台守护进程。
3. **检查并禁用残留的虚拟网卡适配器（Windows / macOS）**：
   - **Windows**：按 `Win + R` 输入 `ncpa.cpl` 打开“网络连接”，查看是否存在依然亮起的 `Meta`、`Clash` 或 `Wintun` 虚拟适配器；如有滞留，右键选择 **「禁用」**，然后再把你正在使用的物理 `WLAN` 或 `以太网` 先右键禁用、等待 3 秒后再启用，迫使操作系统重建干净的默认网关路由。
   - **macOS**：打开 `系统设置 -> 网络 -> VPN 与过滤器`，检查并关闭残留的代理网络扩展或 VPN 描述配置。
4. **还原物理网卡 DNS 为自动获取（DHCP）并关闭残留代理端口**：
   - 检查 Windows `设置 -> 网络和 Internet -> 代理`，确保“使用代理服务器”处于关闭状态。
   - 打开物理网卡 IPv4 属性（macOS 在当前连接 `详细信息 -> DNS`），确认未残留 `127.0.0.1` 或 `198.18.x.x`，保持为 **“自动获得 IP 地址”与“自动获得 DNS 服务器地址”**。
5. **刷新系统 DNS 缓存并验证恢复**：
   - 在 Windows 终端执行 `ipconfig /flushdns`（或 PowerShell `Clear-DnsClientCache`），在 macOS 执行 `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`，清理可能残留在内存中的 `198.18.x.x` Fake-IP 缓存。
   - 打开浏览器测试访问国内基础网页或本地路由器管理页面，确认本地宽带 100% 恢复直连后再查阅核心日志排查原因。

## 七、常见问题

### 既然已经开启了系统代理，为什么终端命令行和部分桌面游戏还是不走代理，必须开 TUN 模式？
系统代理只是操作系统保存的一个本地 HTTP/SOCKS 端口建议，浏览器和少数现代桌面端会主动读取，但终端命令（`git`、`curl`、`npm`、`docker`）、部分 UWP 程序以及绝大多数 UDP 游戏联机默认直接走物理网卡、无视系统代理。TUN 模式通过虚拟网卡在三层网络接口直接接管整台主机的数据包，从而覆盖这些盲区。

### 为什么在 Clash Verge Rev 里打开了 TUN 开关，但命令行和游戏依然走直连没有任何效果？
因为创建虚拟网卡并接管系统默认路由属于高权限内核操作，普通用户态启动软件无权生效。在 Windows 端必须先在客户端设置里安装并激活 Service Mode 服务模式（变成绿色运行状态）；macOS 端则必须输入管理员密码完成辅助程序与网络扩展授权；否则界面开关虽亮，底层并没有真正建立路由接管。

### 什么是路由环路（Routing Loop），为什么开启 TUN 后有时会瞬间全网断流、CPU 飙升？
路由环路是指代理内核自己向远端机场服务器建连的加密数据包，没有经由物理网卡直出，而是又被自己建出来的 TUN 网卡抓回去重新塞进核心处理，形成无限死循环。这多由关闭 `auto-detect-interface`、同时开启了两款软件的虚拟网卡或将上游 DNS 配成会被自身拦截的地址引起。

### 开启 TUN 模式或关闭 TUN 模式后突然整个电脑彻底断网（连国内网站也打不开），如何安全回滚？
请按标准四步执行安全回滚：首先在客户端关闭 TUN 与系统代理开关并彻底退出软件；其次停用后台 Service Mode 服务并确认无残留虚拟网卡活跃；接着把物理网卡的 IPv4 与 DNS 还原为自动获取（DHCP），必要时重启一次物理网卡重置默认路由；最后刷新系统 DNS 缓存清理残留的 `198.18.x.x` 假 IP。绝不要用关闭杀毒软件或强删注册表来处理断网。

### 家里已经部署了 OpenWrt 软路由透明代理，电脑或手机上还需要开启 TUN 模式吗？
不需要，且严禁同时开启。当软路由已经为局域网内全部设备接管了透明代理时，终端设备如果再开启 TUN 或手机 VPN，就会在本地和软路由之间形成双层加密嵌套和 Fake-IP 二次解析死锁，轻则网速大幅下降、重则直接断流。连接已配好透明代理的 Wi-Fi 时请彻底关闭单机代理软件。

### Windows 开启 TUN 模式后导致 WSL2 或 Hyper-V 虚拟机无法上网怎么办？
这通常是开启 TUN 并启用 `strict-route` 后拦截了虚拟交换机的回包，或宿主机未放行来自 WSL 子网的端口连接所致。排查时需确认客户端已开启 `allow-lan` 并在路由配置中排除 WSL 私有子网网段，确保虚拟机与宿主机之间的本地通信不经由 TUN 虚拟网卡转发。

### 如果平时只是偶尔在终端里用一下 git 或 curl，不想长期开启高风险的 TUN 模式有什么替代方案？
完全不需要长期开 TUN。只需在需要使用终端出海的那个窗口里，临时运行环境变量命令将 `HTTP_PROXY` 和 `HTTPS_PROXY` 指向客户端正在监听的本地混合端口（如 `http://127.0.0.1:7897`）即可。该设置仅对当前终端会话有效，关闭窗口立即失效，零驱动风险、不改系统路由表。
