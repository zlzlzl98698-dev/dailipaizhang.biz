# VPN 与代理有什么区别：三层 TUN 隧道 vs 四层/七层分流代理技术原理

## 核心结论（Answer-First）

**传统 VPN** 工作在三层网络层，靠虚拟网卡将整机 IP 报文无差别打包送往远端网关，适合企业内网组网；**现代规则代理** 工作在四层与七层，可识别域名与进程执行毫秒级分流，兼顾国内外速度与公网抗干扰。代理开启 TUN 虽借用了三层虚拟网卡抓包，底层仍由应用层规则引擎驱动，二者在路由粒度上截然不同。

## 一、先破除常见误区：为什么叫法经常混在一起

在中文互联网的日常讨论里，“VPN”“梯子”“代理”“加速器”经常被混用，甚至许多安卓和 iOS 手机在开启代理客户端（如 Shadowrocket、v2rayNG、Clash Meta for Android）时，系统状态栏右上角也会直接亮起一个 **VPN 图标**。这让不少用户误以为「只要亮了 VPN 图标，底层就一定是传统 VPN」。

其实，移动端状态栏之所以出现 VPN 图标，是因为 Android 的 `VpnService` 和 iOS 的 `NetworkExtension (NEPacketTunnelProvider)` 是操作系统唯一允许普通第三方应用在免 Root/免越狱条件下接管全局 IP 数据包的官方接口。代理客户端只是借用了系统提供的虚拟隧道通道把数据包拦截进本地内核，拦截之后到底走三层原包封装，还是拆解还原域名再做七层规则分流，完全取决于客户端内核的架构设计。如果想进一步对照具体协议（如 WireGuard、OpenVPN 与 VLESS、Trojan、Hysteria 2）的握手性能差异，可一并参阅 [VPN 协议与架构全景对比](/vpn/comparisons/)。

## 二、OSI 分层视角：三层 TUN 隧道与四层/七层代理的数据路径

把两套机制放到计算机网络 OSI 模型下拆解，就能一眼看懂数据包从浏览器发出后分别经历了什么：

| 技术维度 | 传统三层 VPN（WireGuard / OpenVPN / IKEv2） | 四层/七层系统代理（HTTP / SOCKS5） | 现代代理 + 本地 TUN 模式（Mihomo / sing-box） |
| :--- | :--- | :--- | :--- |
| **接管层级** | OSI L3 网络层（或 L2 链路层 TAP） | OSI L4 传输层 / L7 应用层 | 入口 L3 虚拟网卡接管 + 内核 L4/L7 规则路由 |
| **接管范围** | 操作系统整机 IP 流量（含 TCP、UDP、ICMP） | 仅主动读取系统代理的浏览器与部分应用 | 整机流量，但可按进程名、域名、IP 段精细放行或直连 |
| **加密封装对象** | 将完整原始 IP 报文直接二次封装进外层隧道包 | 仅对应用层载荷建立代理会话（TCP/UDP 流） | 本地重组 TCP/UDP 流后，按策略封装为 VLESS/SS/Trojan 发出 |
| **域名分流能力** | 弱（传统路由表仅认 IP CIDR，难以感知域名） | 强（客户端直接收到明文域名或 TLS SNI 信息） | 极强（结合 Fake-IP / 嗅探 Sniffing 精准识别域名与地区） |
| **对国内流量影响** | 默认全局绕远，易拖慢国内站点与局域网设备 | 仅代理列表内域名，国内访问与局域网几乎零干扰 | 规则匹配后国内与局域网走直连，兼顾全局接管与本地速度 |
| **典型部署场景** | 企业总部内网接入、异地组网访问内网数据库与 NAS | 日常网页浏览、轻量跨境查询与开发文档检索 | 多地区 AI 工具分流、流媒体解锁、终端 CLI 与跨国游戏 |

> 📚 **权威学术与行业协议规范出处**：
> - 传统四层代理标准参见 IETF **[RFC 1928 (SOCKS Protocol Version 5)](https://datatracker.ietf.org/doc/html/rfc1928)**；
> - 现代现代加密传输层安全参见 IETF **[RFC 8446 (The TLS Protocol Version 1.3)](https://datatracker.ietf.org/doc/html/rfc8446)**；
> - 基于 UDP 的多路复用安全传输规范参见 IETF **[RFC 9000 (QUIC: A UDP-Based Transport)](https://datatracker.ietf.org/doc/html/rfc9000)**。

### 1. 传统三层 VPN 的「套娃封装」逻辑

以 WireGuard 和 OpenVPN（TUN 模式）为例，启动后客户端会在 Windows、macOS 或 Linux 上创建一块虚拟网卡（例如 `wg0` 或 `utun`），随后修改操作系统的路由表，将缺省路由 `0.0.0.0/0` 或企业内网网段（如 `10.0.0.0/8`）指向该虚拟网卡。

当你的电脑向某个目标发出数据包时，操作系统内核直接把完整的 **内层 IP 报文（含源 IP、目标 IP、TCP/UDP 头与载荷）** 交给虚拟网卡。VPN 进程对其执行加密后，在外部套上一层全新的 **外层 IP 头 + UDP/TCP 隧道头**，发往远端 VPN 网关。远端网关解密剥离外层头后，再以网关身份把内层 IP 包转发出去。

这套设计最大的优点是 **对上层软件完全透明**——哪怕是上世纪的工业控制软件、数据库客户端、SMB 局域网文件共享或 ICMP `ping` 探测，只要走 IP 协议，无需任何代理配置就能无缝接入远程内网。但它的短板同样来自三层视野的局限：**内核路由表只认 IP 地址，不认域名**。当一个 CDN 节点同时承载国内外业务、或同一网站频繁更换解析 IP 时，传统三层静态路由表很难做到精准分流，往往只能“一刀切”全局绕行。

### 2. 四层/七层分流代理的「会话重装与规则路由」逻辑

传统系统代理（HTTP Proxy / SOCKS5）并不触碰操作系统路由表，也不创建虚拟网卡，而是在本机监听一个回环端口（例如 Clash Verge Rev 常用的 `127.0.0.1:7897` 或 v2rayN 常用的 `10808`/`10809`）。浏览器或支持代理的客户端直接把 **目标域名字符串**（如 `CONNECT api.openai.com:443`）递交给本地代理内核。

拿到域名后，代理内核（如 Mihomo、Xray 或 sing-box）依次执行四步决策：
1. **规则匹配**：对照本地规则集（`DOMAIN-SUFFIX`、`GEOSITE`、`GEOIP`），判断该目标属于国内直连（`DIRECT`）、广告拦截（`REJECT`）、还是某个专用策略组（如把 AI 服务固定到美国节点、日常网页走香港低延迟节点）。
2. **远端 DNS 解析防污染**：对于判定走代理的域名，直接把域名通过代理协议发给远端落地服务器去解析，彻底绕开本地宽带运营商 DNS 污染（详细原理见 [DNS 污染与泄漏修复](/troubleshooting/articles/dns-leak-hijack-fix)）。
3. **协议封装与多路复用**：内核按当前选中节点的协议（如 Shadowsocks AEAD、Trojan、VLESS-Reality 或 Hysteria 2）建立到远端服务器的加密链路，仅搬运应用层数据流，避免三层 VPN 常见的「TCP over TCP 拥塞雪崩」问题。
4. **按需叠加本地 TUN**：遇到命令行工具、UWP 应用或桌面游戏无视系统代理时，用户再开启代理客户端自带的 TUN 模式。关于系统代理与代理 TUN 模式的切换边界及断网修复，可对照阅读 [TUN 模式与系统代理有什么区别](/troubleshooting/articles/tun-vs-system-proxy)。

## 三、深度对比四大核心工程差异

### 1. MTU 分片与「TCP over TCP」性能陷阱

传统三层 VPN 每次封装都会在原 IP 包外再增加 40–80 字节的隧道与加密开销。如果虚拟网卡的 MTU（最大传输单元）没有下调（通常需从常规 1500 降至 1280–1420），数据包在穿过公网 PPPoE 链路时就会反复触发 IP 分片或路径 MTU 黑洞，表现为「能 ping 通、小网页能开，但发图片、传文件或加载大图立刻卡死」。

此外，当传统 OpenVPN 被迫工作在 TCP 模式时，内层应用（如 HTTPS）自带一套 TCP 重传与拥塞控制，外层隧道又套了一套 TCP 重传。一旦跨境链路出现 3% 以上丢包，内外两层同时触发超时重传，就会出现经典的 **TCP 熔断（TCP Meltdown）**，吞吐瞬间跌至几 KB/s。而现代应用层代理（如 VLESS、Shadowsocks）在本地直接终结应用的 TCP 连接，只把纯字节流交由外层单一 TCP 或 QUIC 连接转发，天然规避了双层 TCP 状态机打架的问题。

### 2. DNS 归属与 Fake-IP 机制的本质不同

传统 VPN 建立后，通常会把整台电脑的 DNS 服务器强行覆盖为远端网关推下来的单一 DNS 地址（例如 `10.8.0.1` 或国外公共 DNS）。这会导致两个连锁反应：一是解析淘宝、微信或公司内网域名时拿到海外 CDN IP，访问国内网站极慢；二是如果操作系统的多网卡跃点数配置不当（尤其是 Windows 的智能多宿主名称解析 SMHNR），DNS 查询可能偷偷从物理网卡漏向本地运营商，造成严重的 **DNS 泄漏**。

现代规则代理则引入了 **分流 DNS + Fake-IP** 架构：内核内置 DNS 服务器同时配置国内外两组上游，并可为命中代理规则的域名瞬间返回保留网段内的虚拟映射地址（`198.18.0.0/16`），省去本地等待真实海外解析的时间，再由远端落地机就近解析出最优海外 CDN。理解这一机制的边界与局域网冲突排除，可参考 [Fake-IP 原理解析与修复](/troubleshooting/articles/fake-ip-explained-fix) 与 [DNS 与 Fake-IP 配置指南](/guides/dns-setup/)。

### 3. 公网流量特征与 DPI 抗干扰能力

在开放公网跨境链路中，传输协议的「外观」直接决定连通率：
- **传统 VPN 特征裸露**：IPsec/IKEv2 绑定固定 UDP 500/4500 端口；OpenVPN 握手报文带有明确的协议操作码；WireGuard 虽极简高效，但握手包大小严格固定（148 字节发起、92 字节响应）且无 TLS 外壳，极易触发公网流量分类与 UDP 惩罚限速。
- **现代代理协议伪装与专线分工**：Trojan 与 VLESS-Reality 直接将流量伪装成标准 HTTPS/TLS 1.3 网页会话，配合浏览器指纹模拟（uTLS），在公网网关视角下几乎与常规访问海外大厂官网无异；而在不经公网审查的物理内网专线（IEPL/IPLC）环境下，机场服务商又常使用头部开销极小的 Shadowsocks 或轻量 VLESS 以换取更高的吞吐效率（参见 [IEPL 专线原理](/routes/iepl/) 与 [光速云品牌评测](/reviews/guangsuyun/) 中的多协议实测差异）。

### 4. 客户端生态与服务商形态边界

很多新手在选工具时容易忽略服务商的协议封闭性：传统商业 VPN 几乎全部绑定自家闭源客户端，只能使用该厂商固定的几个协议与全局模式；而跨境代理生态同时存在两类形态——一类是支持通用订阅链接的服务商（可自由导入 [Clash Verge Rev](/clients/clash-verge/)、[v2rayN](/clients/v2rayn/)、[Shadowrocket](/clients/shadowrocket/) 等开源或独立客户端手写分流规则），另一类则是仅提供自研专属客户端的服务商（例如资料中标注 2026 年 10 月起转向专属端的 [无忧链接](/brands/wuyou/)、[Firefly](/brands/firefly/) 等）。选型前应先确认自己是否需要自定义分流和软路由部署，再决定采用哪套架构。

## 四、场景选型矩阵：什么时候该用 VPN，什么时候该用规则代理

不要用“谁更高级”来评价 VPN 与代理，而应看你的真实网络诉求：

| 使用场景 | 推荐技术架构 | 核心原因与实操提示 |
| :--- | :--- | :--- |
| **连接公司总部内网 / 访问私有 ERP、数据库、SMB 共享** | 传统三层 VPN（WireGuard / OpenVPN / 企业 SSL VPN） | 必须获得公司分配的内网私有 IP 与三层互通路由，普通七层代理无法直接映射企业私有子网 |
| **异地组网回家访问 NAS、监控与路由器后台** | 自建三层 VPN（WireGuard / Tailscale 等） | 端到端加密、配置轻便，支持访问家庭局域网全部非 HTTP 端口设备 |
| **日常跨境查资料、兼顾国内微信/网银/视频不降速** | 四层/七层分流代理（Clash Verge Rev / v2rayN 系统代理） | 按域名毫秒级分流，国内直连零损耗，无需接管整机虚拟网卡，资源占用极低 |
| **多地区 AI（ChatGPT / Claude / Gemini）+ 流媒体精细分流** | 规则代理（独立 `select` 策略组 + 按需开启本地 TUN） | 可同时实现「日常走香港、OpenAI 锁美国、Gemini 锁新加坡、国内直连」，传统 VPN 无法单机多区并发分流 |
| **终端开发（Git / Docker / pip）与海外联机游戏** | 规则代理 + 本地 TUN 模式（或 OpenWrt 透明代理） | 既解决了命令行与游戏无视系统代理的问题，又能只把海外目标送入对应低延迟节点 |

如果你在电脑上既要开公司 VPN 处理内网工作，又需要运行跨境代理访问海外技术文档，切忌直接把两个软件的全局虚拟网卡同时拉起，否则极易触发路由表抢占与双层套娃断网。具体共存排除步骤，请直接查看同专题下的 [VPN 与代理客户端能否同时运行](/vpn/articles/vpn-and-proxy-coexistence) 与 [TUN 模式生效排查](/troubleshooting/articles/tun-not-working)。

## 五、常见问题

### 日常上网和跨境办公，传统 VPN 和规则分流代理最核心的区别是什么？

传统 VPN 工作在 OSI 三层网络层，通过虚拟网卡（TUN/TAP）将整台设备的全部 IP 数据包无差别封装发往远端网关，更适合企业内网接入；而现代代理客户端默认工作在四层传输层或七层应用层，能够读取目标域名并结合本地规则库决定直连或走不同地区节点，既不拖慢国内网站，也便于按站点精细分流。

### 既然现代代理客户端也有 TUN 模式，那开启 TUN 模式后的代理就等于传统 VPN 吗？

不完全等同。代理客户端开启 TUN 模式确实在操作系统侧借用了与 VPN 相同的三层虚拟网卡来拦截全机流量，但在虚拟网卡之后，代理内核会先对 IP 包进行流重组、还原目标域名并执行规则引擎匹配，再通过 VLESS、Trojan 或 Shadowsocks 等应用层代理协议分别转发，而不是像传统 VPN 那样把整个三层 IP 包直接塞进单一远端隧道。

### 为什么用传统企业 VPN 访问国内网站或局域网打印机经常变慢甚至失联？

因为传统 VPN 往往直接向系统写入默认路由（0.0.0.0/0）指向虚拟网卡，导致所有流量都被强制拉到远端 VPN 服务器再绕回公网。如果服务器未下发精细的静态路由排除表，国内视频、即时通讯甚至局域网打印机的流量都会绕远路或被远端防火墙丢弃，进而出现延迟暴涨与局域网失联。

### 在协议加密和隐私保护上，传统 VPN 一定比现代代理更安全吗？

不一定。传输安全性取决于具体的加密套件、认证方式与服务端可信度，而不是“VPN”或“代理”的叫法。WireGuard 与 IPsec 在三层提供强加密，而 VLESS+TLS 1.3 或 Trojan 在七层同样采用现代标准 TLS 加密。真正决定隐私边界的，是服务商是否记录出口日志、客户端是否开源可审以及本地是否存在 DNS 泄漏。

### 为什么跨境弱网环境下，原生 OpenVPN 和 WireGuard 往往比 VLESS 或 Shadowsocks 更容易断流？

原生 OpenVPN 和 WireGuard 设计初衷是可信网络互联，而非流量隐匿。OpenVPN 的握手控制包具有固定明文操作码特征，WireGuard 的 UDP 握手包长度严格固定且无伪装外壳，在跨国公网骨干网中极易被深度包检测（DPI）识别或触发运营商对高端口 UDP 的限速策略；而现代代理协议常叠加标准 TLS 1.3 外壳或专线内网转发，抗干扰能力更强。
