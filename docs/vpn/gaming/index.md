    a: 视频流媒体播放依靠的是 TCP 大包并发吞吐量，播放器本地拥有数十秒的数据预加载缓冲区，瞬时丢包可以通过底层 TCP 重传被掩盖；而竞技类联机游戏与实时语音通讯 95% 以上依赖 UDP 小包的双向毫秒级即时传输，对端到端延迟抖动（Jitter）、丢包率以及 NAT 映射类型极度敏感。如果节点未放行 UDP、存在队列拥塞（Bufferbloat）或限制了并发端口，就会出现吞吐极高但游戏狂卡掉线的脱节现象。

    a: 在标准代理测速工具（如 MAI-TEST-BOT）的自动化报告中，最后一列表示通过 STUN 协议向公网测试服务器发送探测包后的响应结果。若显示 Unknown，通常说明测速脚本后端在测试时未开启 STUN 探测、测试超时，或者该节点服务器在防火墙层面直接封锁了入站/出站的 UDP 转发能力；不能据此推断该节点能够胜任游戏加速需求。

    a: FullCone（完全圆锥型 / NAT 1）允许任何外部主机通过已分配的映射公网端口向你发送数据，对 Switch、主机 P2P 房间联机与语音通话最为顺畅；RestrictedCone（受限型 / NAT 2）仅允许你曾主动发过包的外部 IP 通信，中心化服务器网游可正常游玩；而 Symmetric（对称型 / NAT 4 / Strict）对不同目标每次动态随机分配新端口，会导致 P2P 联机完全失败、好友大厅无法组队或语音单向失聪。
  - q: 主机游戏（Switch / PS5 / Xbox）测试网络时，NAT 类型显示为 C/D 或 Strict 怎么改善？
    a: 造成主机 NAT 严苛的主要原因是家庭网络处于光猫拨号加家用路由器的“双重 NAT”环境。改善步骤包括：第一，联系宽带运营商将光猫改为桥接模式，由性能更强的家用主路由器直接进行 PPPoE 拨号；第二，在主路由器设置中开启 UPnP（通用即插即用）功能；第三，在路由器中将主机的本地 IP 地址加入 DMZ 主机或配置 FullCone NAT 开关；第四，联机时通过网线直连或经由支持主机加速的合规加速硬件。
  - q: 电脑上同时运行游戏加速器和 Clash Verge 时，如何彻底防止虚拟网卡与路由冲突？
    a: 绝不能在开启游戏加速器的同时开启客户端的全局 TUN 虚拟网卡模式，否则两个虚拟网卡驱动会同时争夺 Windows 的默认路由表 metric 跃点，造成游戏进程被代理拦截或加速器闪退。最佳共存方案是：代理客户端仅保留系统代理模式（HTTP/SOCKS5 浏览器端口），在设置中彻底关闭 TUN 模式；或者在 Mihomo 内核中使用 process-name 规则将游戏执行程序明确标记为 DIRECT 直连。
  - q: 为什么反作弊系统（如 EasyAntiCheat、BattlEye、Vanguard）有时会把 TUN 虚拟网卡误判为违规？
    a: 现代竞技游戏的反作弊驱动工作在 Windows 操作系统的 Ring 0 内核层。部分代理客户端安装的第三方 Wintun / TAP 虚拟网卡驱动或网络封包拦截钩子（Hook），如果未经微软数字签名认证或行为类似于网络劫持外挂，可能会触发反作弊系统的内存完整性保护机制，导致游戏报反作弊错误、拒绝启动或闪退。
  - q: 如何在晚高峰（20:00–23:00）准确测试当前网络线路的抖动（Jitter）与丢包率？
    a: 不要在测速网站上仅看一瞬间的测速极值。准确的方法是使用持续长 ping 测试或专业网络诊断工具：在晚高峰时段，向目标游戏服务器所在机房 IP 或特定中转入口连续发送 500 至 1000 个 64 字节的 ICMP / UDP 数据包，计算延迟波动的标准差（Jitter 抖动值）与丢包率百分比；合格的游戏网络环境其 Jitter 应稳定在 3ms 以内且丢包率严格为 0%。

# 游戏加速器与 UDP/NAT 诊断：FullCone、延迟抖动与客户端防冲突指南

**联机游戏从来不看“最大下载带宽能跑到几百兆”，游戏体验的核心指标只有三个：端到端往返时延（RTT）、毫秒级延迟抖动（Jitter）是否收敛在极限阈值内，以及 UDP 报文的 NAT 穿透类型是否处于开放状态。** 很多用户将用于网页浏览和看高清流媒体视频的代理节点直接拿去打外服竞技网游，结果频频遭遇语音无声、好友匹配失败、角色“瞬移回弹（Rubberbanding）”以及游戏掉线封禁。

本指南从底层网络通信协议出发，深度剖析联机游戏的通信特征，系统拆解测速报表中的 NAT 类型，提供科学的晚高峰弱网测试诊断方法，并详细指导如何解决电脑上游戏加速器与代理客户端打架的路由死锁故障。

::: info 游戏加速器与普通代理的本质区别
合规商业游戏加速器面向**指定游戏进程的 UDP 小包**进行路由优化，采用高成本的端对端低抖动专线，内部不做海量视频大并发混跑；而通用规则代理工具面向**全机或浏览器的通用 Web 流量**，主攻 TCP 吞吐量与精细分流，二者的底层 QoS 调度策略与技术取向存在本质不同。
:::

## 一、为什么高速代理节点打游戏依然卡顿？

许多用户常常困惑：在 Speedtest 上测速能跑满 500Mbps 甚至千兆带宽的节点，为什么在《Apex英雄》《反恐精英 2》《使命召唤》或主机联机游戏中，延迟会突然从 40ms 飙升到 200ms，甚至直接掉线？

### 1. TCP 吞吐与 UDP 实时交互的物理鸿沟

- **网页与流媒体的 TCP 大包逻辑**：看 4K 视频时，浏览器或视频 App 是通过 TCP 协议并发拉取分片文件。TCP 具备强大的拥塞控制与超时重传机制，且播放器本地拥有 **10 秒到 30 秒的内存缓冲区**。即使网络在某一瞬间发生 5% 的丢包，TCP 可以在后台默默重传，只要缓冲区没耗尽，画面就毫无卡顿，用户对此完全无感。
- **联机游戏的 UDP 小包无缓存逻辑**：竞技类网游与多人语音（如 Discord 实时通话）95% 以上使用 UDP 报文。游戏客户端与对战服务器之间每秒钟需要相互发送 **60 到 128 次微小数据包**（Tickrate），每个包仅有几十到数百字节，实时同步角色的位置坐标、开火弹道和物理碰撞。
- **无法重传的致命伤**：游戏中的时空状态是不可逆的。0.1 秒前丢失的“玩家移动坐标包”，即便在 0.3 秒后重传回来也已经彻底作废。如果底层网络发生抖动或丢包，服务端只能依靠客户端状态预测算法进行强制插值修正，表现在屏幕上就是玩家瞬间被拉回原地、技能按不出或打中敌人不掉血（Ghost Hits）。

### 2. 缓冲膨胀（Bufferbloat）引发的队列拥塞

在普通公共代理节点上，成百上千名用户共享同一条服务器出口带宽：
- 当同一服务器上的其他用户正在全速下载大文件或缓存 4K 视频时，路由器和虚拟化网卡中的数据包发送队列（Queue）会被海量的大型 TCP 数据包瞬间填满。
- 此时，你的游戏 UDP 小包只能在物理队列末尾痛苦排队等待发送。
- 其结果就是：平时的基础 Ping 只有 40ms，一旦有人开始跑流量，游戏延迟瞬间暴增到 300ms 以上。这种现象在网络工程中被称为**缓冲膨胀（Bufferbloat）**。而专业的游戏加速专线会在入口交换机对 UDP 游戏包施加最高优先级的服务质量（QoS EF 队列）调度，防止被常规下载流量挤占。

## 二、RFC 3489 规范下的四种 NAT 穿透类型全解

在查看网络工具的诊断报告（如 MAI-TEST-BOT 测速结果）或主机网络测试（如 Switch NAT A/B/C/D，PS5 NAT Type 1/2/3）时，`NAT类型` 是决定多人联机成功与否的关键技术指标。

```
STUN 穿透类型示意：
客户端 [内网IP:端口] ──> NAT网关映射为 ──> [公网IP:映射端口]
   ├── FullCone (NAT 1):        任何公网主机均可向此映射端口发送数据（极度开放，P2P极速匹配）
   ├── RestrictedCone (NAT 2):  仅允许已向其发送过数据的外部IP发回数据（限制IP）
   ├── PortRestricted (NAT 3):  仅允许已向其发送过数据的外部IP+端口发回数据（限制IP与端口）
   └── Symmetric (NAT 4):       访问不同外部目标分配不同端口（严格对称，P2P联机噩梦）
```

### 1. FullCone NAT（完全圆锥型 / 对应 NAT 1 或 Type A）

- **技术特征**：一旦内网设备的私有 IP 与端口向外建立了一次连接，NAT 路由网关就会为其分配一个固定的公网 IP 和映射端口。此后，**公网上的任何其他主机，无论此前是否与该设备通信过，都可以通过这个公网 IP 和映射端口直接把 UDP 数据包发还给设备**。
- **游戏影响**：联机环境最理想。在 Nintendo Switch《任天堂明星大乱斗》《马里奥赛车》等强依赖 P2P 房间直连的游戏中，能够秒建房、秒进房；主机联机测试稳获 **Type A**。

### 2. Restricted Cone NAT（受限圆锥型 / 对应 NAT 2 或 Type B）

- **技术特征**：同样分配固定公网映射端口，但网关增加了 IP 地址过滤白名单规则。只有设备先前**主动发送过数据包的外部服务器 IP**，该 IP 发来的 UDP 数据才会被允许穿透进入内网。
- **游戏影响**：绝大多数大型中心化服务器网游（如战地、英雄联盟、绝地求生等所有数据都经过官方固定机房服务器的游戏）可以完全正常运行；在纯 P2P 联机场景下，只要房间内有一名 FullCone 房主充当中继，也可以稳定联机。

### 3. Port-Restricted Cone NAT（端口受限圆锥型 / 对应 NAT 3 或 Type C）

- **技术特征**：在受限圆锥型的基础上进一步收紧，不仅校验源 IP，还必须校验**源端口号**。只有来自设备曾经主动打过招呼的特定外部 IP 且必须是特定端口发回的数据，网关才予以放行。
- **游戏影响**：部分 P2P 游戏开始出现匹配困难，玩家尝试加入好友私人联机房间时经常提示“无法连接到主机”或错误代码。

### 4. Symmetric NAT（对称型 / 对应 NAT 4 或 Type D / Strict）

- **技术特征**：设备每向一个不同的外部 IP 或不同端口发起网络连接，NAT 网关都会在底层**随机动态分配一个全新的公网映射端口**。
- **游戏影响**：**多人联机的终极噩梦**。外部好友主机根本无法预测你当前的公网端口号，导致两台主机之间的 P2P 穿透尝试 100% 失败。表现为：组队大厅频繁掉线、游戏内小队实时语音单向无声、无法被好友搜寻到。

### 5. 测速报表中的“Unknown / Blocked”代表什么？

在查阅历史测速留存记录（例如本站留存的 2026-08-11 批次 MAI-TEST-BOT 测速实测报告）中，常常看到最后一列标为 `Unknown`：
- **成因剖析**：测速机器人通常向预设的公网 STUN 服务器发起双向 UDP 探测。如果该节点后端配置未开启 UDP 转发（如配置中缺少 `udp: true`）、节点所在机房防火墙直接封锁了外发 UDP 报文、或者当时 STUN 探测服务器超时未响应，报表均会统一返回 `Unknown`。
- **技术结论**：标为 `Unknown` 的节点绝不能直接推定为支持 FullCone 游戏加速。如果需要将其用于轻度联机，必须在本地使用专业工具重新验证其 UDP 连通性，详见[UDP 与 NAT 防火墙排查专篇](/troubleshooting/articles/udp-nat-firewall-blocks)。

#### 四种 NAT 模式与游戏兼容性对照全景

| NAT 模式分类 | RFC 3489 定义 | 典型的主机测试等级 | 对 P2P 联机的影响 | 对实时语音对讲的影响 |
|---|---|---|---|---|
| **FullCone** | 完全圆锥型（Open） | Switch Type A / PS5 Type 1 | 极佳，秒匹配，支持做房主 | 极佳，双向音频清晰稳定 |
| **Restricted** | IP 受限圆锥型 | Switch Type B / PS5 Type 2 | 良好，中心化服务器无影响 | 良好，主流语音软件通畅 |
| **Port-Restricted** | 端口受限圆锥型 | Switch Type C / PS5 Type 2/3 | 一般，部分房间加入超时 | 偶尔出现进频道无声 |
| **Symmetric** | 对称型（Strict） | Switch Type D / PS5 Type 3 | 极差，几乎无法加入 P2P 房间 | 极差，频现单向失聪或断线 |

## 三、网络质量核心指标：延迟（Ping）与抖动（Jitter）

不要被测速截图上静态的“Ping 35ms”所迷惑。在网络排障中，**Jitter（抖动）与丢包率的权重大于 Ping 绝对值本身**。

### 1. 什么是 Jitter（延迟抖动）？

Jitter 是指连续发送的多个数据包在端到端往返传输时，**延迟波动的离散程度与差值**：
- **场景对比**：
  - **网络 A（高品质游戏专线）**：平均延迟 60ms。100 个探测包中，延迟稳定在 `58ms、60ms、61ms、59ms`。Jitter 抖动值小于 **2ms**，丢包率 **0%**。实际游戏体验极度丝滑。
  - **网络 B（公网普通中转/拥堵骨干）**：平均延迟也是 60ms。但实际上数据包延迟表现为 `35ms、35ms、190ms、35ms、丢包、240ms`。Jitter 抖动值高达 **40ms 以上**。实际游戏体验中角色会剧烈瞬移，射击判定完全错乱。
- 相关低延迟专线与线路分类的深入分析，可查阅[低延迟线路分析](/routes/low-latency/)与[IPLC 专线与 IEPL 专线机制](/routes/iplc/)。

### 2. 晚高峰（20:00–23:00）抖动与丢包实测方法

验证一条网络线路是否真正胜任联机游戏，必须在晚高峰网络拥塞最高峰时段进行严格的压力测试：

1. **排除本地 Wi-Fi 干扰**：电脑或主机务必使用六类（Cat6）以上千兆网线直接插入路由器千兆 LAN 口，切勿使用隔墙的 2.4G/5G 无线 Wi-Fi 测试，避免无线信道竞争引入本地伪抖动。
2. **利用命令行进行长采样 Ping 测试**：
   在 Windows 命令提示符中向目标服务器 IP 发送 200 次大包测试：
   ```cmd
   ping -n 200 -l 128 <目标服务器IP>
   ```
3. **观察统计输出结论**：
   - **丢包率（Packet Loss）**：必须为 **0%**。在竞技游戏中，即使 1% 的微小丢包都会导致致命的关键操作判定丢失。
   - **最大延迟与最小延迟之差**：二者差值应严格控制在 **10ms 以内**。若最大延迟超过最小延迟 30ms 以上，说明跨网路由上存在严重的队列拥塞或 QoS 限速。晚高峰相关的排错策略见[晚高峰高延迟与丢包排查](/troubleshooting/articles/high-latency-packet-loss-peak)。

## 四、电脑端加速器与代理客户端共存防冲突方案

在实际使用中，很多电脑玩家既需要开着 [Clash Verge Rev](/clients/clash-verge/) 访问海外网页、查攻略或挂着 Discord 语音，同时又需要运行商业游戏加速器来加速 Steam 竞技游戏。**如果设置不当，两套网络工具会在系统内核层激烈冲突，导致两者同时断网**。

### 1. 致命冲突根源：默认路由与虚拟网卡争抢

- 当你在代理客户端中开启了 **TUN 模式** 时，客户端会在 Windows 中安装一个 `Wintun` 虚拟网络适配器，并将其默认网关躍点数（Metric）设置为极低的值，从而强行把系统底层产生的一切 IP 报文全量截获到代理核心中。
- 当你再启动游戏加速器时，游戏加速器通常也会在内核安装自己的虚拟网卡驱动或网络分流钩子。
- 两个虚拟网卡同时争夺系统的默认路由出口，导致数据包在两个虚拟接口之间来回死锁反弹，结果就是加速器提示“网络初始化失败”，代理软件报错“端口已被占用”。TUN 模式的底层机理可参考[TUN 模式与系统代理的区别](/troubleshooting/articles/tun-vs-system-proxy)与[TUN 模式无法运行排错](/troubleshooting/articles/tun-not-working)。

### 2. 完美共存的三种配置实践

```
流量协同分工模式：
全机应用程序 ──> 浏览器 / 网页 / Discord ──> 走 Clash Verge 系统代理模式 (HTTP/SOCKS5 端口)
             ──> 竞技游戏进程 (xxx.exe)    ──> 走专业游戏加速器专属虚拟通道 ──> 直达对战服务器
```

- **最佳实践方案：代理工具退守“系统代理模式”，严禁双开 TUN**
  1. 打开 [Clash Verge Rev](/clients/clash-verge/)，在设置中彻底**关闭 TUN 模式**（确保系统服务模式处于未激活状态）。
  2. 仅开启常规的**「系统代理（System Proxy）」**开关。
  3. 此时，代理软件仅通过操作系统标准环境变链接管 Chrome、Edge 等浏览器的 Web 请求，完全不会向系统底层注入三层路由拦截。
  4. 启动商业游戏加速器，加速器独占三层虚拟网卡，顺畅接管游戏进程的 UDP 数据流，二者井水不犯河水。
- **进阶方案：在 Mihomo 内核中利用进程规则强制 DIRECT**
  如果你必须长期开启代理客户端的 TUN 模式接管其他小众软件，可以在 [Mihomo 配置文件](/clients/mihomo/) 的 `rules` 分流列表中，将游戏主程序的进程名显式标记为直连：
  ```yaml
  rules:
    - PROCESS-NAME,cs2.exe,DIRECT
    - PROCESS-NAME,Apex.exe,DIRECT
    - PROCESS-NAME,Valorant.exe,DIRECT
    - PROCESS-NAME,steam.exe,DIRECT
    # 其余通用流量继续走分流规则
    - GEOIP,CN,DIRECT
    - MATCH,PROXY
  ```
  这样即使全局开启 TUN，核心检测到游戏进程的封包时也会立刻原样放行，允许其被外层的游戏加速器正常捕获。
- **反作弊系统（Anti-Cheat）兼容性规避**
  现代外服游戏的反作弊驱动（如拳头 Riot Vanguard、腾讯 ACE、EasyAntiCheat 等）对系统内核完整性审查极严。如果开启了未经签名的虚拟网卡或抓包软件，反作弊程序会直接拦截并弹窗报错。联机打竞技游戏前，彻底退出未使用的多余网络驱动是保证账号安全的基本操作。

## 常见问题

### 为什么下载测速高达 500Mbps 的节点，打联机游戏和语音通话却频繁卡顿掉线？

视频流媒体播放依靠的是 TCP 大包并发吞吐量，播放器本地拥有数十秒的数据预加载缓冲区，瞬时丢包可以通过底层 TCP 重传被掩盖；而竞技类联机游戏与实时语音通讯 95% 以上依赖 UDP 小包的双向毫秒级即时传输，对端到端延迟抖动（Jitter）、丢包率以及 NAT 映射类型极度敏感。如果节点未放行 UDP、存在队列拥塞（Bufferbloat）或限制了并发端口，就会出现吞吐极高但游戏狂卡掉线的脱节现象。

### 测速报告里最后一列的 UDP 类型写着“Unknown”或“Blocked”到底是什么意思？

在标准代理测速工具（如 MAI-TEST-BOT）的自动化报告中，最后一列表示通过 STUN 协议向公网测试服务器发送探测包后的响应结果。若显示 Unknown，通常说明测速脚本后端在测试时未开启 STUN 探测、测试超时，或者该节点服务器在防火墙层面直接封锁了入站/出站的 UDP 转发能力；不能据此推断该节点能够胜任游戏加速需求。

### FullCone、RestrictedCone 与 Symmetric 对游戏联机匹配到底有什么决定性影响？

FullCone（完全圆锥型 / NAT 1）允许任何外部主机通过已分配的映射公网端口向你发送数据，对 Switch、主机 P2P 房间联机与语音通话最为顺畅；RestrictedCone（受限型 / NAT 2）仅允许你曾主动发过包的外部 IP 通信，中心化服务器网游可正常游玩；而 Symmetric（对称型 / NAT 4 / Strict）对不同目标每次动态随机分配新端口，会导致 P2P 联机完全失败、好友大厅无法组队或语音单向失聪。

### 主机游戏（Switch / PS5 / Xbox）测试网络时，NAT 类型显示为 C/D 或 Strict 怎么改善？

造成主机 NAT 严苛的主要原因是家庭网络处于光猫拨号加家用路由器的“双重 NAT”环境。改善步骤包括：第一，联系宽带运营商将光猫改为桥接模式，由性能更强的家用主路由器直接进行 PPPoE 拨号；第二，在主路由器设置中开启 UPnP（通用即插即用）功能；第三，在路由器中将主机的本地 IP 地址加入 DMZ 主机或配置 FullCone NAT 开关；第四，联机时通过网线直连或经由支持主机加速的合规加速硬件。

### 电脑上同时运行游戏加速器和 Clash Verge 时，如何彻底防止虚拟网卡与路由冲突？

绝不能在开启游戏加速器的同时开启客户端的全局 TUN 虚拟网卡模式，否则两个虚拟网卡驱动会同时争夺 Windows 的默认路由表 metric 跃点，造成游戏进程被代理拦截或加速器闪退。最佳共存方案是：代理客户端仅保留系统代理模式（HTTP/SOCKS5 浏览器端口），在设置中彻底关闭 TUN 模式；或者在 Mihomo 内核中使用 process-name 规则将游戏执行程序明确标记为 DIRECT 直连。

### 为什么反作弊系统（如 EasyAntiCheat、BattlEye、Vanguard）有时会把 TUN 虚拟网卡误判为违规？

现代竞技游戏的反作弊驱动工作在 Windows 操作系统的 Ring 0 内核层。部分代理客户端安装的第三方 Wintun / TAP 虚拟网卡驱动或网络封包拦截钩子（Hook），如果未经微软数字签名认证或行为类似于网络劫持外挂，可能会触发反作弊系统的内存完整性保护机制，导致游戏报反作弊错误、拒绝启动或闪退。

### 如何在晚高峰（20:00–23:00）准确测试当前网络线路的抖动（Jitter）与丢包率？

不要在测速网站上仅看一瞬间的测速极值。准确的方法是使用持续长 ping 测试或专业网络诊断工具：在晚高峰时段，向目标游戏服务器所在机房 IP 或特定中转入口连续发送 500 至 1000 个 64 字节的 ICMP / UDP 数据包，计算延迟波动的标准差（Jitter 抖动值）与丢包率百分比；合格的游戏网络环境其 Jitter 应稳定在 3ms 以内且丢包率严格为 0%。
