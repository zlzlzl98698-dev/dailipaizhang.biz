faq:
  - q: 为什么 iPhone 锁屏几分钟或切换大型 App 后，小火箭或代理扩展就自动断开了？
    a: 苹果 iOS 系统对 NetworkExtension（NEPacketTunnelProvider）后台扩展进程施加了严格的内存上限（通常为 15MB 至 50MB 之间，视系统版本而定）。当订阅规则列表过度臃肿、加载了过大的 GeoIP/GeoSite 数据库、开启了全量抓包日志或发生高并发连接时，扩展进程一旦触碰系统内存红线就会被操作系统内核瞬间强制终止（OOM 机制）。
  - q: 为什么手机系统在同一时刻只能开启一个活跃的 VPN 或代理工具？
    a: 无论是 iOS 的 NetworkExtension 还是 Android 的 VpnService，在未获取 Root 或越狱的普通用户空间中，操作系统底层只设计了一个虚拟网络适配器槽位来接管系统全局默认路由。当第二个网络工具请求建立隧道时，系统内核会自动注销并断开前一个工具的会话，属于操作系统层面的底层互斥安全机制。
  - q: 手机从家里 Wi-Fi 切换到户外 5G 移动蜂窝网络时断流假死，怎样快速恢复？
    a: 网络切换会导致本地设备分配到的物理 IP 地址与默认网关变更，原有的底层 TCP Socket 连接与 TLS 会话会全部失效。若客户端未开启自动重连或使用的节点未启用会话快速恢复，数据流就会停滞。最快速的恢复方法是下拉状态栏开启飞行模式 3 秒后关闭，或者在客户端界面内手动断开并重新连接一次。
  - q: 为什么开启了海外节点，部分社交或短视频 App 依然能准确识别出我的国内真实位置？
    a: 移动端应用程序获取地理位置的方式非常多维，除了根据出口 IP 判定外，还会直接读取手机 SIM 卡的 MCC/MNC 国家运营商代码、系统的语言与地区设置、基站定位信号以及 GPS 硬件坐标。若要避免识别，需要针对应用权限进行综合管控，而不能仅依赖网络层面的代理隧道。
  - q: 手机开启代理后耗电速度明显增加且机身发热，如何通过精简规则集进行优化？
    a: 手机每发起一次网络请求，代理客户端都需要将目标域名与本地规则库中的成千上万条规则进行逐一模式匹配。规则集越庞大、正则表达式越复杂，CPU 唤醒频率和计算负荷就越高。优化方法包括：精简非必要的广告屏蔽规则、改用二叉树查找的规则集文件、关闭未使用的抓包日志记录，以及启用仅代理指定应用的分流模式。
  - q: 手机开启热点共享时，连接热点的电脑或平板能直接走手机上的代理网络吗？
    a: 默认情况下不能。绝大多数智能手机系统在开启移动热点时，其热点流量在操作系统底层是通过特定网络命名空间（Network Namespace）直接与蜂窝网卡进行网络地址转换（NAT）直连转发，根本不会穿过用户态的 VpnService 或 NetworkExtension 虚拟网卡。要让热点走代理，需要借助局域网共享模式或支持热点中继的高级客户端功能。
  - q: 如何防止手机端因 IPv6 或 WebRTC 直连而绕过代理隧道泄露真实 IP？
    a: 移动运营商的 5G/4G 蜂窝网络普遍原生下发 IPv6 双栈地址。如果手机代理客户端没有配置完整的 IPv6 拦截路由，应用发起 IPv6 请求时就会直接穿透代理发往运营商公网；此外，浏览器或部分客户端中的 WebRTC 协议可能通过 STUN 穿透暴露真实 IP。解决方法是在客户端设置中开启禁用 IPv6 开关，并在规则中将直连模式收紧。

# 手机 VPN 与移动代理排障指南：iOS / Android 机制、保活与切网优化

**在电脑桌面上能够连续稳定运行数天的网络节点，移植到智能手机上往往会出现锁屏十分钟就断流、切换 Wi-Fi/5G 时陷入假死、或者后台突然闪退等现象。这绝大多数并非节点服务商的技术故障，而是移动操作系统为了控制整机功耗、限制内存占用和隔离安全沙箱所做出的底层设计。**

智能手机运行环境与桌面操作系统截然不同。手机时刻处于移动网络基站切换、息屏深度休眠、前后台任务冻结以及动态电量调度的复杂场景中。只有深入理解 iOS 与 Android 系统的核心权限模型与网络栈实现，才能从根源上解决移动端断流、发热、耗电与真实 IP 泄露问题。

::: info 架构前提：移动端网络工具的本质
在非越狱（Jailbreak）的 iPhone 或免 Root 的 Android 手机上，所有的商业 VPN、企业远程接入软件以及第三方规则代理客户端（包括 [Shadowrocket](/clients/shadowrocket/)、sing-box 移动端、[v2rayN](/clients/v2rayn/) 对应的 v2rayNG 以及各类自研端），其底层全部依赖系统提供的公用虚拟网络适配器 API 运行。
:::

## 一、底层权限模型对比：iOS NetworkExtension vs Android VpnService

了解两个主流移动操作系统的底层网络接管框架，是理解一切手机网络排障逻辑的基础。

### 1. iOS 系统：NetworkExtension 与独立的沙箱扩展进程

在苹果 iOS / iPadOS 系统中，第三方开发者无法直接修改系统全局路由表。所有网络接管功能必须通过官方的 `NetworkExtension.framework` 框架实现，其中最核心的组件是 `NEPacketTunnelProvider`。

- **进程隔离机制**：当你在 [Shadowrocket](/clients/shadowrocket/) 或 sing-box iOS 版中点击“连接”开关时，iOS 实际上是在后台独立启动了一个由系统托管的扩展进程（Extension Process），而主 App 界面进程甚至可以被直接划掉关闭。
- **严苛的内存配额限制（Memory Limit）**：为了防止网络扩展耗尽手机有限的运行内存（RAM），iOS 内核为 NetworkExtension 施加了极为苛刻的物理内存上限。在早期系统版本中该上限甚至低至 15MB 左右，在现代 iOS 17 / 18 系统中通常也限制在 **30MB 至 50MB** 的狭窄区间内。
- **OOM 瞬间强杀**：一旦该扩展进程在处理巨量规则匹配、大体积 GeoIP 数据库反序列化、或者并发大量高吞吐数据流时，内存占用哪怕瞬间超出了系统配额 1KB，iOS 系统的内存看门狗（Jetsam）就会在零点几毫秒内直接向进程发送 `SIGKILL` 信号将其无情抹杀。此时系统状态栏顶部的 VPN 图标瞬间消失，网络连接彻底中断，且用户界面上通常没有任何崩溃弹窗提示。
- **按需连接（Connect On Demand）**：iOS 原生提供了按需连接能力。系统允许在特定 Wi-Fi 网络 SSID 下自动激活或暂停 VPN，也可以配置为当应用发起 DNS 请求时由操作系统内核自动拉起扩展，这一特性是实现 iOS 端无感后台保活的核心技术支撑。

### 2. Android 系统：VpnService 与前台服务保活框架

Android 系统的实现方式与 iOS 大相径庭。Google 从 Android 4.0 开始引入了标准的 `android.net.VpnService` API。

- **前台服务（Foreground Service）依赖**：Android 系统对后台进程有着极强的回收倾向。为了保证 `VpnService` 建立的虚拟网络接口（如 `tun0`）不被系统清理，应用程序必须将自己声明为一个附带持续常驻通知栏卡片的“前台服务”。如果用户在系统设置中彻底屏蔽了该软件的通知栏权限，Android 系统可能会在息屏休眠时将其直接判定为普通后台进程并予以清理。
- **单隧道互斥模型**：无论是 Android 原生系统还是各大厂商的定制 ROM（如小米澎湃 OS、华为鸿蒙、OPPO ColorOS、vivo OriginOS 等），系统在同一时刻只允许全局存在一个活动的 `VpnService` 实例。当第二个应用发起连接请求时，系统内核会自动撤回对前一个应用的授权。
- **原生分应用代理能力**：相比 iOS 需要由客户端自己在应用层进行复杂的域名与 IP 规则匹配，Android 系统在操作系统底层就原生支持了应用包名级的分流能力（通过 `VpnService.Builder.addAllowedApplication` 与 `addDisallowedApplication` 实现）。这使得安卓端在实现精细化分流时，其 CPU 计算开销和内存负担往往远低于 iOS。深入的安卓端优化可参阅[安卓 VPN 与分应用深度指南](/vpn/android/)。

#### iOS 与 Android 移动网络隧道对比全景表

| 比较维度 | 苹果 iOS / iPadOS 平台 | 谷歌 Android 平台 |
|---|---|---|
| **底层核心接口** | `NEPacketTunnelProvider`（NetworkExtension） | `android.net.VpnService` 接口 |
| **运行进程模型** | 独立于主 App 的轻量系统扩展进程 | 主 App 内置的前台服务进程 |
| **内存限制（RAM）** | **极度严苛（约 15MB–50MB 硬性红线）** | 受常规 Android 应用虚拟机堆内存限制（宽松） |
| **常见异常崩溃原因** | 内存超标触发系统 Jetsam 强杀（OOM 闪退） | 厂商定制 ROM 激进电池优化与杀后台策略 |
| **系统保活机制** | 依赖 Connect On Demand 按需拉起 | 依赖前台通知栏常驻 + 电池白名单加锁 |
| **分应用分流支持** | 仅支持基于目标域名与 IP 的规则匹配 | 原生支持基于应用程序包名（Package Name）的分流 |
| **状态栏指示图标** | 顶部状态栏显示固定 `VPN` 字符图标 | 顶部通知栏显示钥匙（Key）或专用网络图标 |

## 二、移动基站切换与 Wi-Fi 漫游断流全解

现代智能手机在日常使用中会频繁在不同的网络物理媒介之间跃迁：从家里的 5G Wi-Fi 走到楼道切换为运营商 4G/5G 蜂窝基站，在地铁行驶过程中连续跨越数十个通信基站塔，或者在不同楼层之间漫游于多个无线路由器 AP 之间。

### 1. 移动网络切换的底层网络震荡

当网络媒介发生改变时，底层的物理通信链路经历了剧烈的变化：
- **物理出口 IP 变更**：当你从家庭宽带断开并连上蜂窝数据时，手机网卡绑定的本地真实 IP 地址瞬间发生了改变，默认网关也由局域网路由器重置为运营商基站核心网网关。
- **底层 Socket 连接全部失效**：所有正在进行的底层 TCP 连接（包括你的客户端与远端节点服务器之间建立的传输通道）因为通信源 IP 的改变，全部在物理层事实上断开。
- **移动基站切换引起的瞬时丢包**：在高速移动场景下，手机从一个基站切换到另一个基站的过程中，信令面与用户面交接（Handover）可能会产生数百毫秒至数秒的网络中断。如果此时客户端使用的通信协议没有良好的容错恢复机制，整机网络就会瞬间陷入“信号显示满格，但任何网络数据都发不出去”的假死状态。

### 2. 传输协议在移动弱网下的抗震荡表现

不同的网络传输协议在面对基站切换和无线弱网时的抗性差异极大：
- **传统 TCP / TLS 协议（如标准 VLESS-TCP、Trojan）**：由于 TCP 严格依赖三次握手与滑动窗口机制，一旦底层物理网络断开，原有的 TCP 连接就会处于等待超时或重传状态。在网络切换后，客户端必须从零开始重新向节点发起 DNS 解析、TCP 握手和 TLS 证书协商，这个过程通常需要消耗 1 至 3 秒甚至更长的时间。
- **基于 QUIC / UDP 的新一代协议（如 Hysteria 2、WireGuard）**：QUIC 协议内置了**连接迁移（Connection Migration）**机制。QUIC 连接不再通过传统的 IP + 端口四元组来标识连接，而是使用一个独立的 Connection ID。当手机物理网络从 Wi-Fi 切换到 5G 时，只要 Connection ID 保持不变，客户端只需向远端发送一个新的数据包即可无缝恢复数据传输，无需重新握手，在基站切换时能够实现近乎零感知的平滑过渡。协议特性的深入对比见[VPN 软件与协议架构对比](/vpn/comparisons/)。

### 3. 切网假死的四步急救法

在日常使用中如果遇到切网后网络卡死：
1. **下拉控制中心快速开关飞行模式**：开启飞行模式 3 秒钟后关闭。这会强制断开手机射频基带的物理供电，迫使操作系统清空本地一切残留的 Socket 状态表与 DNS 解析缓存，重新向最近的基站注册并协商数据通道。
2. **在客户端内手动重置开关**：点击客户端界面的断开按钮，等待 2 秒后再点击连接，促使内核重新绑定当前活跃的网络网卡。
3. **检查节点的 UDP 放行情况**：如果你的节点使用的是基于 UDP 的协议，而所在区域的移动运营商基站对特定高端口 UDP 存在严重的 QoS 丢包或阻断，网络可能会持续中断。此时可在客户端中尝试将节点切换为标准的 TCP/TLS 节点。网络延迟与丢包排障可查阅[晚高峰高延迟与丢包排查](/troubleshooting/articles/high-latency-packet-loss-peak)。
4. **验证节点连接状态**：如果重置网络后依旧无法恢复，检查是否节点服务器本身遭遇故障或订阅到期，对照[节点全部超时排查](/troubleshooting/articles/nodes-all-timeout)进行确认。

## 三、发热与耗电优化：规则集精简实战

在手机上开启网络工具后，许多用户会明显感觉到手机续航缩短、机身中上部发热。除了加解密计算本身的开销外，90% 以上的异常耗电源于**臃肿劣质的规则集与不恰当的系统唤醒**。

### 1. 耗电元凶：巨量规则集导致的 CPU 持续唤醒

手机上的网络交互是高度碎片化的。后台有数十个 App 处于长轮询状态，系统通知服务（如 APNs、HMS、厂商推送通道）每隔几十秒就会产生微小的数据包交换。
- **字符串匹配与正则回溯开销**：如果你的客户端配置中引入了多份动辄数万行的广告屏蔽列表、冗长的自定义规则或者复杂的正则表达式，每当系统产生一次 DNS 解析或网络连接请求时，手机 CPU 就必须在内核层被强行从低功耗休眠状态唤醒，并在内存中对这数万条规则进行逐一比对。
- **内存反复换页**：庞大的规则表会长期霸占珍贵的缓存空间，在 CPU 密集匹配时不仅加剧了电量消耗，还会产生明显的机身发热，并最终增加被系统 Jetsam 机制当作耗电大户强杀的风险。

### 2. 精简移动端规则的三项核心策略

为了让手机兼顾流畅与长续航，移动端应当遵循“极简高效”的配置原则：
- **策略一：剥离庞大的网页广告过滤规则**：将广告拦截的任务交给专业的浏览器扩展（如 Safari 原生内容拦截器），而不是让整个代理扩展的虚拟网卡去充当防火墙。移动端代理客户端应当只专注于区分“需要走节点的域名”与“国内直连的域名”。
- **策略二：采用二叉搜索的 GeoSite / GeoIP 数据库**：优先使用经过预编译和二叉树优化的规则格式（例如 sing-box 的 `.srs` 规则集或 Mihomo 的专用数据库），这种格式支持纳秒级的内存索引查询，其 CPU 计算消耗仅为传统纯文本逐行匹配的几十分之一。
- **策略三：关闭全量日志记录与数据持久化**：在客户端设置中，将日志级别调整为 `warning` 或 `error`，并彻底关闭“记录所有访问请求（HTTP Request Logging）”与“抓包历史保存”功能。持续向手机闪存写入日志不仅拖慢 I/O 速度，也是导致后台耗电的隐形杀手。

## 四、移动端定位识别、SIM 卡信息与防漏隔离

许多用户常常困惑：“为什么我的手机明明已经挂上了海外合规节点，打开某些社交软件、短视频客户端或海外电商平台时，应用依然能一秒识别出我的国内真实身份？”

### 1. 移动设备多维度环境识别体系

在移动操作系统上，应用获取你所处地理位置的途径远远不止“查看你的网络 IP”这一条通路：

```
移动端位置侦测维度：
├── 1. 网络层出口 IP（代理隧道接管部分）
├── 2. SIM 卡 MCC/MNC 运营商国际识别码（应用无需定位权限即可直接读取）
├── 3. 系统语言、时区与地区格式（zh-CN, GMT+8）
├── 4. GPS / 北斗卫星高精度硬件定位（依赖用户弹窗授权）
├── 5. 附近 Wi-Fi 路由器的 BSSID 物理热点扫描定位
└── 6. 运营商基站塔 Cell ID 蜂窝基站粗略定位
```

- **SIM 卡运营商识别码（MCC/MNC）**：这是最容易被忽视的泄露源。国际移动用户识别码中包含了移动国家代码（MCC）和移动网络代码（MNC）。例如中国移动的代码为 `46000`，中国联通为 `46001`。在 Android 和 iOS 平台上，绝大多数应用**无需向用户申请任何隐私定位权限，即可通过系统基础通信接口直接读取当前插槽中 SIM 卡的 MCC/MNC 编码**。一旦应用读取到 `460` 开头的中国国家识别码，便可直接锁定你的国内身份。
- **基站与 Wi-Fi 扫描定位**：现代地图 SDK 会在后台静默扫描手机周围能够搜索到的无线路由器 MAC 地址（BSSID）和手机连接的蜂窝基站塔编号，并与全球基站数据库进行比对，其定位精度可以精准到数米之内，这一过程完全绕过任何网络代理隧道。

### 2. 移动端防泄漏与银行 App 分流实操配置

为了确保国内关键业务（如手机银行、个人所得税、各类政务办事软件、网购外卖软件）能够秒开且不被风控，同时保障海外业务的纯净度，必须实施严格的分流隔离：
- **避免手机银行异地风控**：国内金融与银行类 App 对 IP 变动极为敏感。如果登录网银时流量不慎穿过海外节点，极易触发银行的风控拦截系统，甚至导致账户被临时冻结。在客户端配置中，必须将国内常见银行域名、支付平台以及 `DIRECT` 直连规则置于规则列表顶端。分流规则的详细配置方法见[分流规则设置指南](/guides/split-routing/)。
- **关闭高精度定位授权**：对于不需要定位功能的海外社交与资讯类应用，在手机「系统设置 -> 隐私与安全性 -> 定位服务」中将其定位权限彻底设置为“永不”。
- **针对特定纯净环境的测试策略**：在进行跨国业务环境兼容性验证时，专业技术人员通常会采用拔出物理 SIM 卡、开启飞行模式仅保留 Wi-Fi、并在系统中将时区与系统语言与目标区域严格同步的标准化操作流程。

## 五、手机移动热点共享的代理穿透限制

在出差或户外移动办公场景下，很多人喜欢用手机开启个人热点供笔记本电脑或平板使用，并期望电脑能直接享用手机上开启的代理通道。

### 1. 为什么默认情况下热点无法走手机代理？

从计算机网络体系结构来看：
- 手机开启代理时，系统创建的 `tun0` 虚拟网卡只拦截了**本设备自身应用层所产生的网络套接字（Local Socket）**。
- 当手机开启“个人热点（Tethering）”功能时，操作系统内核充当的是一个传统的网络路由器角色。从其他电脑通过 Wi-Fi 发送到手机上的数据包，直接进入了操作系统的网络地址转换（NAT）内核转发流水线，并在物理网卡与蜂窝网卡之间直接进行了报文路由，**根本不会被向上递交给用户态的 VpnService 虚拟网卡**。
- 其最终结果是：手机自身看网页走的是代理节点，但连入热点的笔记本电脑访问的却全部是手机蜂窝网络的未代理公网直连流量！

### 2. 实现热点共享代理的两种可靠方案

- **方案 A：开启客户端的“局域网共享 / 允许局域网连接”功能**
  1. 在手机代理客户端（如 Clash Meta for Android、Shadowrocket 等）设置中，找到并开启「允许来自局域网的连接（Allow LAN）」开关。
  2. 记下客户端提示的局域网端口（例如 HTTP 代理端口 `7890` 或 SOCKS5 端口 `7891`）。
  3. 打开手机的 Wi-Fi 设置，查看手机当前在热点内网中所分配到的 IP 地址（通常形如 `192.168.43.1` 或 `172.20.10.1`）。
  4. 在连接了热点的笔记本电脑上，打开网络与代理设置，手动配置 HTTP 代理服务器，将代理 IP 填写为手机的热点 IP，端口填写为上述端口号。
- **方案 B：在笔记本电脑上独立运行客户端**
  相比复杂的手机端共享设置，更为推荐且稳定的方案是**在笔记本电脑上直接安装独立的桌面客户端**（如 [Clash Verge Rev](/clients/clash-verge/) 或 [v2rayN](/clients/v2rayn/)），并在电脑中导入同一份订阅配置。手机仅充当纯粹的物理流量热点通道，这种模式下连接更稳定，且彻底避免了因手机休眠而导致电脑频频掉线的窘境。多平台客户端的安装可查阅[多平台客户端配置指南](/guides/installation/)。

## 六、移动端安全加固：阻断 IPv6 与 WebRTC 泄漏

在移动蜂窝网络下，真实 IP 泄漏的概率比固定宽带更高，主要由于移动运营商全网推行的 IPv6 策略。

### 1. 蜂窝网络 IPv6 绕过风险与防御

三大运营商在 4G/5G 移动核心网上均默认开启了完整的 IPv6 支持，手机通常会分配到一个全球唯一的公网 IPv6 地址。
- 如果手机代理客户端仅配置了 IPv4 的虚拟网卡路由，当应用程序尝试向具备 IPv6 记录（AAAA 记录）的网站发起请求时，系统内核会自动优先采用 IPv6 直连。
- 数据包将直接绕过你的代理客户端，从运营商蜂窝网络向外发出，导致真实网络位置完全裸露。
- **防御配置**：在手机客户端的通用设置中，务必寻找并勾选**「禁用 IPv6（Disable IPv6）」**或**「仅路由 IPv4」**选项。确保客户端通过丢弃或拒绝 AAAA 解析请求，强迫所有应用程序回落到受到安全隧道保护的 IPv4 通道中。系统级的详细排错可参考[DNS 污染与泄漏排查](/troubleshooting/articles/dns-leak-hijack-fix)。

### 2. 移动端账号登录安全与凭证保护

在手机移动端使用网络工具时，务必保持高度的资产安全意识：
- 切勿在公共共享节点或来历不明的免费网络环境下登录涉及个人核心资产的网银、证券或关键企业账户。
- 对于管理订阅与购买服务的账户，务必遵循严格的安全规范，配置独立的复杂密码并启用双因素身份认证（2FA），详细加固指南见[账号安全防护指南](/security/account-security/)与[隐私保护专题](/security/privacy/)。

## 常见问题

### 为什么 iPhone 锁屏几分钟或切换大型 App 后，小火箭或代理扩展就自动断开了？

苹果 iOS 系统对 NetworkExtension（NEPacketTunnelProvider）后台扩展进程施加了严格的内存上限（通常为 15MB 至 50MB 之间，视系统版本而定）。当订阅规则列表过度臃肿、加载了过大的 GeoIP/GeoSite 数据库、开启了全量抓包日志或发生高并发连接时，扩展进程一旦触碰系统内存红线就会被操作系统内核瞬间强制终止（OOM 机制）。

### 为什么手机系统在同一时刻只能开启一个活跃的 VPN 或代理工具？

无论是 iOS 的 NetworkExtension 还是 Android 的 VpnService，在未获取 Root 或越狱的普通用户空间中，操作系统底层只设计了一个虚拟网络适配器槽位来接管系统全局默认路由。当第二个网络工具请求建立隧道时，系统内核会自动注销并断开前一个工具的会话，属于操作系统层面的底层互斥安全机制。

### 手机从家里 Wi-Fi 切换到户外 5G 移动蜂窝网络时断流假死，怎样快速恢复？

网络切换会导致本地设备分配到的物理 IP 地址与默认网关变更，原有的底层 TCP Socket 连接与 TLS 会话会全部失效。若客户端未开启自动重连或使用的节点未启用会话快速恢复，数据流就会停滞。最快速的恢复方法是下拉状态栏开启飞行模式 3 秒后关闭，或者在客户端界面内手动断开并重新连接一次。

### 为什么开启了海外节点，部分社交或短视频 App 依然能准确识别出我的国内真实位置？

移动端应用程序获取地理位置的方式非常多维，除了根据出口 IP 判定外，还会直接读取手机 SIM 卡的 MCC/MNC 国家运营商代码、系统的语言与地区设置、基站定位信号以及 GPS 硬件坐标。若要避免识别，需要针对应用权限进行综合管控，而不能仅依赖网络层面的代理隧道。

### 手机开启代理后耗电速度明显增加且机身发热，如何通过精简规则集进行优化？

手机每发起一次网络请求，代理客户端都需要将目标域名与本地规则库中的成千上万条规则进行逐一模式匹配。规则集越庞大、正则表达式越复杂，CPU 唤醒频率和计算负荷就越高。优化方法包括：精简非必要的广告屏蔽规则、改用二叉树查找的规则集文件、关闭未使用的抓包日志记录，以及启用仅代理指定应用的分流模式。

### 手机开启热点共享时，连接热点的电脑或平板能直接走手机上的代理网络吗？

默认情况下不能。绝大多数智能手机系统在开启移动热点时，其热点流量在操作系统底层是通过特定网络命名空间（Network Namespace）直接与蜂窝网卡进行网络地址转换（NAT）直连转发，根本不会穿过用户态的 VpnService 或 NetworkExtension 虚拟网卡。要让热点走代理，需要借助局域网共享模式或支持热点中继的高级客户端功能。

### 如何防止手机端因 IPv6 或 WebRTC 直连而绕过代理隧道泄露真实 IP？

移动运营商的 5G/4G 蜂窝网络普遍原生下发 IPv6 双栈地址。如果手机代理客户端没有配置完整的 IPv6 拦截路由，应用发起 IPv6 请求时就会直接穿透代理发往运营商公网；此外，浏览器或部分客户端中的 WebRTC 协议可能通过 STUN 穿透暴露真实 IP。解决方法是在客户端设置中开启禁用 IPv6 开关，并在规则中将直连模式收紧。
