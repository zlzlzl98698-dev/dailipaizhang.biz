faq:
  - q: 为什么打开控制台或 ping 域名时返回了 198.18.0.x，这是电脑中病毒或被劫持了吗？
    a: 不是被外部恶意劫持，也不是中病毒，而是代理客户端开启了 Fake-IP 模式（使用 RFC 2544 保留测试网段 198.18.0.0/15）。客户端会先返回一个本地虚拟 IP 暂代真实解析以加速分流匹配；但如果退出客户端后系统 DNS 缓存未及时刷新，或者微信、企业内网软件缓存了该虚拟地址，就会引发断网或加载异常。
  - q: 开启代理后，浏览器里的「使用安全 DNS（DoH）」应该打开还是关闭？
    a: 在系统级使用 Clash Verge Rev、Mihomo、sing-box 或 v2rayN 等规则分流客户端时，建议关闭浏览器内置的安全 DNS（DoH）。因为浏览器直接向外部 DoH 服务器发起加密解析会绕过代理客户端的本地 DNS 拦截，极易导致国内网站被调度到海外 CDN 变卡、分流规则失效或 Fake-IP 映射错乱。
  - q: 开启 Fake-IP 后电脑微信发图片转圈、局域网 NAS 或公司内网 OA 打不开怎么办？
    a: 这是因为相关国内 IM、局域网后缀或企业内网域名没有被纳入客户端的 fake-ip-filter 放行白名单，导致软件拿到了 198.18.x.x 虚拟地址而无法完成直连校验。首选低风险方案是在覆写配置中补全局域网后缀（如 *.lan、*.local）与内网域名白名单；若公司内网存在顽固兼容冲突，则可将增强模式切换为 redir-host（真实 IP）并刷新系统缓存。
  - q: 把 Windows 或 macOS 物理网卡的 DNS 直接改成 8.8.8.8 能解决 DNS 污染吗？
    a: 不仅不能彻底解决污染，反而常常让国内网络变慢甚至异常。第一，明文向 8.8.8.8 发起的 UDP 53 端口查询在跨境链路中依然会被污染或丢包；第二，国内视频、网盘和电商域名如果经由海外公共 DNS 解析，会被 CDN 调度到绕远的境外节点，拖慢加载速度。物理网卡应保持默认自动获取（DHCP），由代理客户端内置加密分流 DNS 接管国内外查询。
  - q: 关闭代理软件后浏览器报 DNS_PROBE_FINISHED_NXDOMAIN，如何最快恢复上网？
    a: 这通常是客户端异常退出未能把网卡 DNS 从本地回环地址还原，或系统缓存里残留着失效的 198.18.x.x 映射。第一步检查操作系统网络适配器属性，将 IPv4/IPv6 DNS 恢复为「自动获取 DNS 服务器地址」；第二步刷新本机 DNS 缓存（Windows 执行 ipconfig /flushdns，macOS 刷新 mDNSResponder 缓存），随后重启浏览器即可恢复。
  - q: 做 DNS 泄漏测试（如 browserleaks / ipleak）看到国内运营商 DNS 出口，一定代表代理失效了吗？
    a: 要区分测试页面本身走的是规则分流还是全局代理。如果测试站点被规则分到了国内直连，看到本地运营商 DNS 属于正常预期；但如果测试域名明确走了海外代理节点，检测结果里却同时冒出国内运营商 DNS 服务器，才说明发生了真正的 DNS 泄漏，通常源于浏览器 DoH 旁路、系统网卡 IPv6 DNS 泄漏或客户端未正确分离海外加密解析通道。
  - q: 软路由 OpenWrt 开启 OpenClash 或 PassWall2 后，局域网设备频繁出现域名解析超时该查哪里？
    a: 软路由 DNS 故障九成源于 dnsmasq 上游转发与代理插件 DNS 端口劫持相互打架，形成解析环路。应核对 OpenWrt 的 DHCP/DNS 设置中是否关闭了冲突的忽略解析文件选项、确认仅由单一代理插件接管 53 端口重定向，同时将局域网本地域名与 NTP 时间服务器域名加入放行白名单，修改前务必先备份路由器配置。

# DNS 错误排查：污染、泄漏与 Fake-IP 异常修复

## 核心结论（Answer-First）

在代理排障实践中，凡是遇到**「代理明明连着却报 `DNS_PROBE_FINISHED_NXDOMAIN`」**、**「电脑微信图片转圈、局域网 NAS 或公司 OA 连不上」**、**「关闭代理软件后国内网页彻底断网」**，或者**「国内网站变卡、海外网站疑似被劫持」**，根因几乎全部集中在 **DNS 解析路径与客户端分流策略错位**。

想要一次根治而不反复折腾，只需紧盯三条核心排障主线：**Fake-IP（`198.18.0.1`）映射冲突与残留清理**、**浏览器/系统自带 DoH 抢解析导致的绕过与泄漏**，以及**直连国内 DNS 与海外加密 DNS 分组配置错配**。全篇严格执行**「现象 → 可能原因 → 低风险检查 → 操作路径 → 验证标准 → 回滚提示」**六步规范，强调「改网卡 DNS 前必先留档、随时可一键还原 DHCP」的安全底线，并直接衔接站内 2 篇核心 DNS 实操指南与多篇关联配置文档。

## 二、核心原理拆解：代理环境里一次域名解析究竟经历了什么

在普通直连网络下，应用向系统查询域名，系统发包给路由器或运营商 DNS，拿回真实 IP 后发起连接。但在分流代理环境下，为了同时满足「国内网站命中就近 CDN 不绕路」与「海外网站不遭本地明文 DNS 污染」，客户端必须接管解析链路并引入两种主流工作模式：

| 对比维度 | Fake-IP 模式（`198.18.0.0/15`） | Redir-Host 模式（真实 IP 模式） |
| :--- | :--- | :--- |
| **底层工作方式** | 收到域名查询瞬间立即返回一个本地保留测试段虚拟 IP（`198.18.0.x`），客户端内存记录映射表，等到真实流量抵达时再按域名匹配分流规则 | 先向配置的国内外 DNS 发起真实解析拿到真实 IP，再依据域名与 GeoIP 规则决定直连还是走代理 |
| **核心优势** | 几乎消除本地 DNS 等待耗时，响应极快；天然避免海外域名在本地向运营商发起明文查询，防泄漏能力强 | 返回给所有本地应用的均为真实公网或内网 IP，对企业内网、NAS、强校验软件与命令行脚本兼容性极高 |
| **典型痛点与风险** | 若 `fake-ip-filter` 漏配，会导致微信、游戏联机、NTP 校时、公司 OA 与局域网设备异常；客户端崩溃后缓存残留会导致直连断网 | 依赖正确的国内外 DNS 拆分策略，否则容易出现国内解析变慢或海外域名在本地触发明文污染 |
| **最佳适用场景** | 日常网页浏览、流媒体与海外办公主力环境（配合完整 `fake-ip-filter`） | 重度依赖企业内网、私有 NAS、本地开发联调或频繁测试网络连通性的排障环境 |

## 三、场景一：Fake-IP（198.18.0.1）残留与微信/局域网异常修复

`198.18.0.0/15` 是国际标准 RFC 2544 预留给网络设备基准测试的专用私有网段，公网上不存在该网段的真实网站。绝大多数基于 Mihomo（Clash Verge Rev / FlClash / OpenClash）或 sing-box 的客户端默认借助这段地址运行 Fake-IP。

### 1. 为什么微信、局域网与退端直连最容易中招？

- **微信 / 钉钉图片与语音异常**：部分国内即时通讯与音视频软件内置了复杂的连接探测、STUN 穿透或直连 IP 缓存逻辑。如果它们的探测域名拿到了 `198.18.x.x` 假地址，客户端内部逻辑会误判网络环境异常，表现为聊天文字能发但图片加载转圈、文件传输极慢或语音无法接通。
- **局域网 NAS、打印机与公司 OA 失联**：局域网设备通常通过 `.lan`、`.local`、`.home.arpa` 或公司内网私有后缀寻址。如果这些内网域名被 Fake-IP 截胡，连接请求会被送进代理核心而非直接发往局域网交换机，最终彻底失联。
- **关闭代理客户端后全网瘫痪**：软件正常退出时会自动清理托管的 DNS 设置，但遭遇闪退、任务管理器强杀或系统休眠异常时，操作系统 DNS 缓存里仍死死记着「某某常用域名 = `198.18.0.12`」，甚至物理网卡的 DNS 栏还停留在 `127.0.0.1` 或 `198.18.0.2`。此时代理核心已经关闭，发往 `198.18` 的数据包自然石沉大海。

### 2. Fake-IP 冲突与残留的六步排查闭环

- **现象**：在终端执行 `ping` 或 `nslookup` 测试国内常规域名或局域网主机时，解析结果落入 `198.18.x.x` 网段；开启代理时微信图片转圈、局域网 NAS 连不上；关闭客户端后浏览器大面积报错无法解析域名。
- **可能原因**：配置文件缺失或过简的 `fake-ip-filter` 放行清单；客户端异常退出后物理网卡 DNS 未恢复自动获取；操作系统或应用进程自身（如浏览器、微信）持久缓存了过期的 `198.18` 映射；TUN 模式与 Fake-IP 叠加在特定内网下触发路由冲突。
- **低风险检查**：打开终端输入 `nslookup www.baidu.com` 与 `nslookup` 你的内网域名，观察返回的 IP 段与当前响应的 DNS Server 地址；同时查看操作系统网络适配器属性，确认 IPv4 与 IPv6 的 DNS 当前是自动获取（DHCP）还是被写死为 `127.0.0.1` / `198.18.0.2`。
- **操作路径**：
  1. **补齐 `fake-ip-filter` 白名单（首选低风险）**：在客户端配置或全局覆写中，将常见局域网后缀（`*.lan`、`*.local`、`*.arpa`）、系统联网检测域名（`*.msftconnecttest.com`、`*.msftncsi.com`）、NTP 授时域名（`time.*.com`、`ntp.*.com`）、STUN 穿透域名以及你所在公司的私有内网域名全部加入 `fake-ip-filter`，让它们直接获取真实 IP。
  2. **清理退端残留（断网急救）**：先彻底关闭代理客户端，将物理网卡 IPv4/IPv6 DNS 恢复为「自动获取（DHCP）」，随后在终端刷新系统 DNS 缓存——Windows 执行 `ipconfig /flushdns`，macOS 执行 `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`，Linux 视服务执行 `resolvectl flush-caches`，最后彻底重启微信或浏览器清空应用内缓存。
  3. **必要时切回 `redir-host` 对照**：若公司内网存在高度复杂的私有域名体系导致白名单难以穷举，在客户端 DNS 配置中将 `enhanced-mode` 临时改为 `redir-host` 重载核心并清缓存验证。
- **验证标准**：关代理后 `nslookup` 国内域名返回真实公网 IP，浏览器直连畅通；开代理后微信图片秒开、局域网 NAS 与海外网站同步可用，且国内直连与内网域名不再落入 `198.18` 段。
- **回滚提示**：编辑 `fake-ip-filter` 或切换 `enhanced-mode` 前，务必先导出备份当前原始配置与覆写脚本；若切换 `redir-host` 后发现海外解析变慢，直接还原原覆写并补全单条内网白名单即可。完整配置模板与逐端操作见 [Fake-IP 原理与 198.18.0.1 异常修复](/troubleshooting/articles/fake-ip-explained-fix)。

## 四、场景二：DNS 污染、DNS 泄漏判断与浏览器 DoH 抢解析

许多用户明明开着代理，却在访问某些海外站点时收到 `DNS_PROBE_FINISHED_NXDOMAIN` 或跳转到奇怪的警告/空白页，或者用泄漏检测工具一查，满屏都是本地宽带运营商的 DNS 服务器地址。这说明加密代理隧道虽已建立，但域名解析阶段出现了「偷跑」或「被投毒」。

### 1. 浏览器安全 DNS（DoH）为什么会和代理客户端打架？

现代 Chrome、Edge 与 Firefox 浏览器普遍默认开启了「使用安全 DNS（DNS over HTTPS）」。在没有代理软件的普通环境下它能防运营商劫持，但在运行 Clash / sing-box / v2rayN 的电脑上，它却常常变成隐蔽的破坏者：

- **绕过本地客户端拦截**：浏览器会把域名查询直接打包成加密 HTTPS 请求发往外部 DoH 提供商，彻底跳过操作系统的系统 DNS 与客户端的 Fake-IP / 规则分流引擎。
- **引发规则失效与 CDN 绕路**：客户端看不到浏览器实际请求的域名，只能看到一堆冷冰冰的 IP 连接，导致基于域名的分流规则（如 `DOMAIN-SUFFIX`）大量失灵；更糟的是，若外部 DoH 走海外解析了国内电商或视频域名，或者走国内运营商 DoH 解析了海外域名，就会同时制造国内卡顿与海外污染双重灾难。

### 2. 科学解读 DNS 泄漏测试结果（避免误判恐慌）

在 `browserleaks.com/dns` 或 `ipleak.net` 等在线检测工具上看到国内运营商 DNS，**不要立刻认定代理泄密**，请按以下两步判断：

1. **先看当前分流模式**：在常规「规则（Rule）」模式下，如果测试网站本身的随机子域名被分流到了直连，或者你的系统在后台并行发起直连探测，看到本地 DNS 很正常。真正的泄漏测试必须在确认测试站点**明确命中海外代理出站**的前提下观察结果。
2. **排查三大真实泄漏源**：若测试站已走海外节点却依然检出国内运营商 DNS，九成逃不出三件事——浏览器独立 DoH 抢解析、物理网卡开启了 IPv6 导致系统直接通过运营商 IPv6 DNS 发包、或者客户端 DNS 配置里把国内明文 DNS 和海外 DNS 混写在同一个 `nameserver` 池里并发竞速。

### 3. DNS 污染与泄漏的六步诊断闭环

- **现象**：代理已连接，但部分海外域名报 `DNS_PROBE_FINISHED_NXDOMAIN`、证书不匹配或解析至异常 IP；开启代理后国内主流视频、电商网站明显卡顿绕路；在确认测试页走代理的前提下，泄漏检测仍出现国内运营商 DNS 出口。
- **可能原因**：浏览器内置安全 DNS（DoH）绕过客户端分流；客户端配置未启用内置 DNS 或未区分国内 `nameserver` 与海外加密 `fallback` / `nameserver-policy`；用户手动把操作系统物理网卡 DNS 改成了单一海外公共 DNS（如 `8.8.8.8`）；本机或路由器 IPv6 DNS 绕过 IPv4 代理隧道；OpenWrt 软路由下 `dnsmasq` 与代理插件 DNS 重定向配置冲突。
- **低风险检查**：打开 Chrome / Edge「设置 → 隐私和安全 → 安全 → 使用安全 DNS」，确认其当前状态；检查操作系统网络适配器 IPv4 与 IPv6 DNS 是否曾被手动篡改；打开客户端实时连接日志，刷新目标站点，核对日志里显示的是**真实域名匹配**还是只剩**纯 IP 连接**（如果大量海外网站只显示纯 IP 而无域名，高度怀疑浏览器 DoH 旁路）。
- **操作路径**：
  1. **关闭浏览器独立 DoH**：在 Chrome / Edge / Firefox 中将「使用安全 DNS」设为关闭，把全部域名解析调度权交还给代理客户端统一按规则分发。
  2. **还原物理网卡默认 DNS**：切勿在物理网卡上硬填 `8.8.8.8` 或 `1.1.1.1` 作为系统全局 DNS；将 Windows/macOS 物理网卡还原为自动获取（DHCP），或指向可信本地局域网网关。
  3. **检查客户端国内外加密 DNS 分离**：确认配置已启用 `dns.enable: true`，国内域名经由低延迟国内加密 DNS（如阿里/腾讯 DoH/DoT）就近解析以保国内 CDN 速度，海外域名则交由经代理隧道转发的加密 DNS（或配合 Fake-IP 交由远端落地机解析）彻底阻断本地明文 UDP 53 污染。具体模板参见 [DNS 与 Fake-IP 标准配置教程](/guides/dns-setup/)。
  4. **软路由 OpenWrt 核查**：确认仅保留一套活跃代理插件（如 OpenClash 或 Nikki，注意 Nikki 要求 OpenWrt 24.10 及以上版本）接管 DNS，排查 `dnsmasq` 上游服务器配置防止与代理插件互指形成死循环。
- **验证标准**：客户端连接日志准确显示各站点的完整域名与规则命中情况；国内站点就近命中本地 CDN 秒开；海外站点无 `NXDOMAIN` 与证书异常；在代理出站前提下复测 DNS 泄漏，出口与预期海外解析通道一致。
- **回滚提示**：修改系统网卡 DNS、路由器 DHCP/DNS 或客户端覆写策略前，必须先截图记录原始设置（尤其是静态 IP 与公司内网专属 DNS 地址）；一旦调整后出现企业内网失联或全网无法解析，立刻恢复截图记录的原始参数并刷新系统 DNS 缓存即可无损回滚。全流程实操见 [DNS 污染、泄漏与标准分流检查路径](/troubleshooting/articles/dns-leak-hijack-fix)。

## 五、场景三：OpenWrt 软路由 dnsmasq 端口劫持冲突与双栈 IPv6 DNS 泄漏

相比单台电脑，家庭或工作室部署了 OpenWrt 软路由（运行 OpenClash、Nikki 或 PassWall2）的环境更容易出现「全屋设备同时域名解析超时、智能家居掉线、手机连接 Wi-Fi 提示无互联网」等连锁 DNS 故障。这类问题几乎全落在软路由底层 `dnsmasq` 与代理插件的 53 端口接管顺序上。

- **现象**：软路由自身可以 `ping` 通公网 IP，但局域网内电脑、手机和电视访问国内外网页均报错解析超时；或者 IPv4 流量已正常走代理，但在泄漏检测里不断冒出本地运营商的 IPv6 DNS 服务器。
- **可能原因**：
  1. **多层 DNS 转发形成死循环**：OpenWrt 默认由 `dnsmasq` 监听 53 端口，若用户在 `dnsmasq` 上游填了代理插件的本地 DNS 端口，而代理插件的 `default-nameserver` 又指向了路由器自身网关地址，请求就会在两者之间无限打转直至超时。
  2. **双代理插件或多款去广告工具抢占 53 端口**：同时启用了 AdGuard Home、SmartDNS 与代理插件的 DNS 劫持功能，却未理清谁做前端、谁做上游转发，导致数据包丢弃。
  3. **IPv6 DNS 绕过分流规则**：宽带光猫下发了运营商原生 IPv6 DNS，局域网设备优先通过 IPv6 向运营商直连查询海外域名，直接绕过了路由器里的 IPv4 代理 DNS 劫持。
- **低风险检查**：登录 OpenWrt 后台，只读检查「网络 → DHCP/DNS → 常规与转发」页面中的上游转发列表与「忽略解析文件」勾选状态；核对是否同时安装了两套及以上代理或去广告插件；检查「接口 → LAN → DHCP 服务器 → IPv6 设置」是否向局域网通告了运营商直连 IPv6 DNS。
- **操作路径**：先在 OpenWrt「系统 → 备份与升级」下载一份完整配置备份；确保同一时刻仅由**单一核心插件**（如 OpenClash 或要求 OpenWrt 24.10 及以上版本的 Nikki）接管 DNS 重定向；为代理核心的引导解析（`default-nameserver`）填写明确的纯 IP 国内公共 DNS（避免再指回路由器自身）；在不需要原生 IPv6 代理转发的家庭环境中，关闭 LAN 口向下游通告外部 IPv6 DNS 或启用插件内置的 IPv6 DNS 过滤，彻底堵住双栈泄漏缺口。
- **验证标准**：局域网内手机与电脑断开重连 Wi-Fi 后，国内网站秒开、智能家居与局域网 NAS 稳定在线，海外域名无 `NXDOMAIN` 且双栈测试不再出现运营商 DNS 泄漏。
- **回滚提示**：修改任何 `dnsmasq`、防火墙劫持或 LAN 接口 IPv6 选项前务必先下载配置压缩包；一旦改错导致局域网无法解析域名，只需用终端手动指定静态网关 IP 登录路由器后台上传备份包，一分钟即可完整恢复出厂前正常状态。

## 六、全平台 DNS 缓存刷新与系统 DNS 还原速查表

当你刚切换了 `fake-ip` / `redir-host` 模式、刚从异常崩溃的 TUN 退回直连，或者刚改完配置却发现旧错误依旧顽固存在时，往往是因为系统层与浏览器层还攥着旧缓存。按平台对照下方只读检查与低风险清理步骤执行即可：

| 平台环境 | 查看当前生效 DNS（只读） | 刷新本机 DNS 缓存动作 | 还原默认自动获取（DHCP）回滚入口 |
| :--- | :--- | :--- | :--- |
| **Windows 10 / 11** | `ipconfig /all` 或 `nslookup example.com` | 终端运行 `ipconfig /flushdns` | 控制面板/设置 → 网络适配器属性 → IPv4/IPv6 → 自动获得 DNS |
| **macOS** | `scutil --dns` | `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder` | 系统设置 → 网络 → 当前连接 → 详细信息 → DNS（清空手动项） |
| **Linux (systemd)** | `resolvectl status` | `sudo resolvectl flush-caches` | NetworkManager / `netplan` 恢复自动 DNS 并重载连接 |
| **Chrome / Edge 浏览器** | 地址栏打开 `chrome://net-internals/#dns` | 点击页面内「Clear host cache」并关闭再重启浏览器 | 设置 → 隐私和安全 → 安全 → 关闭独立安全 DNS |
| **iOS / Android** | 系统 Wi-Fi 详情页查看 DNS 配置 | 开关一次飞行模式（约 5 秒）强制刷新系统解析缓存 | 当前 Wi-Fi 设置 → 配置 DNS → 改回「自动」 |

## 七、修改系统与路由器 DNS 前的四条安全红线

1. **先记录、后修改**：无论是在 Windows 网卡属性、macOS 网络配置还是 OpenWrt 路由后台，修改前必须先截图留存原 IP、子网掩码、网关与原始 DNS 列表，尤其身处公司固定 IP 内网环境时不可盲点自动获取覆盖静态信息。
2. **拒绝全量硬填单一海外公共 DNS**：把电脑网卡 DNS 直接写成 `8.8.8.8` 既防不住本地明文 UDP 53 污染，又会让国内视频、游戏更新和云盘被调度到跨洋慢速节点，属于最常见的反向优化。
3. **不随意叠加多个 DNS 劫持工具**：不要在同一台电脑或同一台软路由上同时运行 AdGuard Home、SmartDNS、两套代理客户端且彼此抢占 53 端口；每多一层未经规划的转发，定位污染和环路的成本就翻倍。
4. **切勿通过关闭安全软件排障**：DNS 异常与杀毒软件几乎无关，遇到权限报错或配置不生效时，应从配置语法、端口占用与系统权限入手核查。

## 常见问题

### 为什么打开控制台或 ping 域名时返回了 198.18.0.x，这是电脑中病毒或被劫持了吗？

不是被外部恶意劫持，也不是中病毒，而是代理客户端开启了 Fake-IP 模式（使用 RFC 2544 保留测试网段 198.18.0.0/15）。客户端会先返回一个本地虚拟 IP 暂代真实解析以加速分流匹配；但如果退出客户端后系统 DNS 缓存未及时刷新，或者微信、企业内网软件缓存了该虚拟地址，就会引发断网或加载异常。

### 开启代理后，浏览器里的「使用安全 DNS（DoH）」应该打开还是关闭？

在系统级使用 Clash Verge Rev、Mihomo、sing-box 或 v2rayN 等规则分流客户端时，建议关闭浏览器内置的安全 DNS（DoH）。因为浏览器直接向外部 DoH 服务器发起加密解析会绕过代理客户端的本地 DNS 拦截，极易导致国内网站被调度到海外 CDN 变卡、分流规则失效或 Fake-IP 映射错乱。

### 开启 Fake-IP 后电脑微信发图片转圈、局域网 NAS 或公司内网 OA 打不开怎么办？

这是因为相关国内 IM、局域网后缀或企业内网域名没有被纳入客户端的 fake-ip-filter 放行白名单，导致软件拿到了 198.18.x.x 虚拟地址而无法完成直连校验。首选低风险方案是在覆写配置中补全局域网后缀（如 *.lan、*.local）与内网域名白名单；若公司内网存在顽固兼容冲突，则可将增强模式切换为 redir-host（真实 IP）并刷新系统缓存。

### 把 Windows 或 macOS 物理网卡的 DNS 直接改成 8.8.8.8 能解决 DNS 污染吗？

不仅不能彻底解决污染，反而常常让国内网络变慢甚至异常。第一，明文向 8.8.8.8 发起的 UDP 53 端口查询在跨境链路中依然会被污染或丢包；第二，国内视频、网盘和电商域名如果经由海外公共 DNS 解析，会被 CDN 调度到绕远的境外节点，拖慢加载速度。物理网卡应保持默认自动获取（DHCP），由代理客户端内置加密分流 DNS 接管国内外查询。

### 关闭代理软件后浏览器报 DNS_PROBE_FINISHED_NXDOMAIN，如何最快恢复上网？

这通常是客户端异常退出未能把网卡 DNS 从本地回环地址还原，或系统缓存里残留着失效的 198.18.x.x 映射。第一步检查操作系统网络适配器属性，将 IPv4/IPv6 DNS 恢复为「自动获取 DNS 服务器地址」；第二步刷新本机 DNS 缓存（Windows 执行 ipconfig /flushdns，macOS 刷新 mDNSResponder 缓存），随后重启浏览器即可恢复。

### 做 DNS 泄漏测试（如 browserleaks / ipleak）看到国内运营商 DNS 出口，一定代表代理失效了吗？

要区分测试页面本身走的是规则分流还是全局代理。如果测试站点被规则分到了国内直连，看到本地运营商 DNS 属于正常预期；但如果测试域名明确走了海外代理节点，检测结果里却同时冒出国内运营商 DNS 服务器，才说明发生了真正的 DNS 泄漏，通常源于浏览器 DoH 旁路、系统网卡 IPv6 DNS 泄漏或客户端未正确分离海外加密解析通道。

### 软路由 OpenWrt 开启 OpenClash 或 PassWall2 后，局域网设备频繁出现域名解析超时该查哪里？

软路由 DNS 故障九成源于 dnsmasq 上游转发与代理插件 DNS 端口劫持相互打架，形成解析环路。应核对 OpenWrt 的 DHCP/DNS 设置中是否关闭了冲突的忽略解析文件选项、确认仅由单一代理插件接管 53 端口重定向，同时将局域网本地域名与 NTP 时间服务器域名加入放行白名单，修改前务必先备份路由器配置。
