# 所有节点同时超时（All Timeout）排查：本地时间、连通性与全局异常分流

## 核心结论（Answer-First）

所有节点同时显示 `Timeout`，极少是全部海外服务器同时宕机，九成源于单点共性故障：本地断网或双代理软件冲突、系统时间偏差导致 TLS/AEAD 鉴权被拒、测速 URL 失效引发“假超时”，或套餐已到期、入口全量变更但本地仍用旧配置。按“核对时间与直连、更新订阅、换网交叉验证”三步，可在三分钟内分清本地与远端故障。

## 故障现象

- **Clash Verge Rev / Mihomo**：在“代理（Proxies）”面板点击测速图标后，所有地区节点延迟均变为红色 `Timeout` 或 `-1`，日志提示 `dial tcp ...: i/o timeout` 或 `EOF`。
- **v2rayN**：全选节点执行 `真连接延迟测试` 后，全部返回 `-1` 或 `超时`，而此前同一批节点工作正常。
- **Shadowrocket / v2rayNG**：底部连通性测试提示 `Timeout` 或 `无法连接服务器`，网页一直处于转圈加载状态。
- **核心区分特征**：并非仅日本或香港单个地区失效，而是香港、新加坡、日本、美国等**全部节点同时不可用**。

## 先做 3 个低风险检查

1. **先关闭代理开关测试本地直连**：把客户端系统代理和 TUN 模式全部关闭，用浏览器打开一个国内常规新闻站或搜索引擎。如果直连本身就打不开，说明是本地 Wi-Fi/宽带掉线或此前残留的错误代理设置堵死了网络，与机场节点无关。
2. **检查设备时钟是否准确**：VMess、VLESS、Trojan 及各类 TLS 协议对时间戳极为敏感（尤其是 VMess 要求误差通常在 90 秒以内）。确认设备时间已开启自动校准。
3. **尝试直接访问一个海外网页测试真实连通（而非仅看面板测速数字）**：有时面板延迟测速并发过高会触发本地端口或中转网关短暂限流，单选一个平时较稳的节点开启代理后直接访问网页，确认是“真断联”还是“测速假超时”。

## 分层原因排除

### 本地系统与网络

- **系统时钟偏差超过协议容忍阈值**：Windows 与 Linux 双系统切换、笔记本长期休眠后系统时钟未同步，会导致基于时间戳校验或 TLS 证书验证的节点被服务端静默丢弃或握手拒绝。
- **多代理客户端并行冲突**：同时打开了 Clash Verge Rev、v2rayN、游戏加速器或公司 VPN，多个软件争抢系统代理或虚拟网卡路由，造成所有发往节点入口的流量被送入无效环路而超时。
- **本地网络环境策略切换**：刚从家用宽带切换到校园网、酒店 Wi-Fi 或公司内网，新的局域网防火墙封锁了非 `80/443` 端口或直接拦截了代理中转 IP。

### 客户端与核心配置

- **延迟测试 URL 失效或超时时间设置过短**：如果测速地址填写了已被阻断或失效的 URL，或者把测速超时设为 `500ms` 而跨国链路首包需要 `800ms`，所有节点都会统一报 `Timeout`。
- **配置文件过于陈旧**：机场已经升级了中转入口域名、更换了端口或调整了传输协议（如从 WS 改为 gRPC/Reality），但本地一直未成功更新订阅，仍在往废弃端口发包。

### DNS 与路由分流

- **节点服务器域名解析失败**：如果节点配置中的服务器地址填写的是域名而非纯 IP，一旦本地 DNS 故障或域名解析遭到污染，客户端连节点入口 IP 都解析不出来，表现为全节点同时超时。
- **路由环路（Routing Loop）**：TUN 模式下未排除当前本地出站网卡或未设置正确的 `auto-route` 跳过规则，节点自己的出站握手包又被送回 TUN 虚拟网卡，引发全部连接死循环超时。

### 远端订阅与节点

- **套餐到期、流量耗尽或并发超限**：这是最容易被忽略的原因——服务端检测到账户超额后停止转发该用户的 UUID/密码，客户端发出的握手包得不到响应或被服务端直接 Reset，表现为全节点超时。
- **机场中转入口集群故障或上游清退**：如果所有节点共享同一组国内/跨境中转入口服务器，当入口主机遭遇维护、被上游机房拔线或遭受大规模流量攻击时，即使后端落地机正常，所有节点也会在同一时间全部显示超时。
- **机场停运或更换主域**：服务商未提前通知而整体关停或迁移集群。

## 操作路径

### 步骤 1：校准本地时间并验证当前直连网络与节点域名解析

**命令 A：检查系统时间同步状态与直连网络（Windows PowerShell）**

- **适用 OS**：Windows 10 / Windows 11
- **目的**：核对 Windows 时间服务状态与本地直连出网是否正常，排除系统时差和本地断网。
- **风险等级**：低风险（只读状态查询）。
- **预期输出解读**：对比 `Get-Date` 与当前真实北京时间；`w32tm /query /status` 可确认时间源是否正常同步；`Test-NetConnection` 对公共常规站点 `443` 端口应返回 `TcpTestSucceeded : True`。

```powershell
Get-Date -Format "yyyy-MM-dd HH:mm:ss zzz"
w32tm /query /status
Test-NetConnection -ComputerName www.baidu.com -Port 443
```

**命令 B：检查系统时间与直连基础连通（macOS / Linux / OpenWrt）**

- **适用 OS**：macOS、Linux、OpenWrt（SSH 终端）
- **目的**：确认本机 UTC 时间准确且关闭代理变量后能正常建立出站 TCP/HTTPS 连接。
- **风险等级**：低风险（只读时间与出站请求测试）。
- **预期输出解读**：若 `date -u` 与当前标准 UTC 时间误差超过 1 分钟，须立即同步时间；`curl` 应快速返回 `HTTP/2 200` 或 `HTTP/1.1 200`，若此处也超时，说明本地网络本身不通。

```bash
date -u
env -u http_proxy -u https_proxy -u all_proxy curl -I -sS --max-time 5 https://www.baidu.com | head -n 3
```

> **iOS / Android 说明**：手机端请先关闭 Shadowrocket / v2rayNG / Clash Meta 的连接开关，确保自带浏览器能够打开正常国内网页，并检查系统时间是否设为“自动确定日期和时间”。

### 步骤 2：排查客户端环境、测速 URL 与更新订阅

1. **退出冲突软件**：检查任务管理器或状态栏，确保没有同时开启第二个代理软件、游戏加速器或企业 VPN。
2. **测试更换延迟检测 URL**：
   - 在 **Clash Verge Rev** 的“设置 → 测试链接”中，确认使用的是标准连通性检测 URL（如 `http://www.gstatic.com/generate_204` 或 `https://cp.cloudflare.com/generate_204`），并将单次超时适当放宽至 `3000–5000ms` 后，仅选 1–2 个节点点击单测（不要一键全部并发测速）。
   - 在 **v2rayN** 的“设置 → 参数设置 → 核心基础设置”中核对测速 URL，改用“单节点右键 → 测试真连接延迟”确认。
   - **iOS / Android / OpenWrt**：分别在 Shadowrocket 设置里切换连通性测试方法（TCP vs URL）、在 v2rayNG 检查测试地址、在 OpenClash 检查测速链接与核心日志。
3. **手动更新一次订阅并核对账户后台**：登录机场网页后台，检查套餐有效期、剩余流量与最新公告；在客户端关闭“使用代理更新”后重新拉取一次最新订阅。

### 步骤 3：跨网络交叉验证，分流“本地网络限制”与“机场全局故障”

- 断开当前宽带/Wi-Fi，改用手机蜂窝热点（或切换不同运营商网络）再次测速。
- **判定矩阵**：
  - **换手机热点后立刻全绿可用**：说明机场节点没问题，是原 Wi-Fi/宽带运营商、光猫或局域网防火墙封锁了对应端口或中转 IP。
  - **更新了最新订阅且换了网络后，依然 100% 全部节点 Timeout，且后台已确认有流量未到期**：几乎可确定是机场中转服务器全局维护、遭遇阻断或服务商全局异常。

## 什么结果算修复

- 校准时间、清理冲突或更新订阅后，单个节点真连接测试延迟恢复为正常数值（常见香港/日本/新加坡节点在 `30ms–250ms` 区间，欧美节点在 `140ms–350ms` 区间），不再显示 `Timeout` 或 `-1`。
- 客户端实时日志中 `dial tcp` 握手成功建立，开启系统代理或 TUN 后可正常打开多类海外测试网页。

## 若仍失败怎么办

1. **若发现是更新订阅本身也失败**：转向 [更新订阅失败：401/403/404/503 与被重定向排查](/troubleshooting/articles/sub-http-401-403-404-503) 或 [更新订阅 TLS 与超时排查](/troubleshooting/articles/sub-tls-dns-timeout)。
2. **若怀疑套餐或旧配置问题**：查看 [套餐到期、流量耗尽与客户端旧配置过时的快速区分](/troubleshooting/articles/quota-expired-vs-stale-config) 核对面板特征。
3. **若确认机场全局失联且无恢复公告**：不要盲目重装系统，先查看 [机场跑路识别与止损步骤](/security/shutdown/) 与 [服务失联替代方案](/security/alternatives/)，启用备用服务或切换其他通道。

## 高风险操作与回滚提示

- **严禁关闭杀毒软件或彻底关闭操作系统防火墙**：遇到全节点超时时，部分教程会误导用户直接关闭 Windows Defender 或第三方安全软件，这不会修复远端中转断联或时间漂移，反而会让系统暴露在恶意风险中。
- **严禁在网上公开晒出带完整节点服务器 IP/UUID 或含 Token 订阅链接的日志截图**：在社区求助时，日志里的服务器地址、用户 UUID 和订阅 Token 均需打码脱敏。
- **修改系统时间同步与防火墙/代理规则后的回滚**：
  - 若手动关闭了自定义时间同步或改用过自定义 NTP 服务器，Windows 可执行 `w32tm /config /syncfromflags:domhier /update` 或在“设置 → 时间和语言”重新打开“自动设置时间”和“自动设置时区”即可回滚；macOS / Linux 开启系统标准 `timedatectl set-ntp true`。
  - 若测试期间修改过客户端的测试 URL 或超时参数，记录原默认值（如 `http://www.gstatic.com/generate_204`、超时 `5000ms`），排查结束后直接改回默认值。

## 常见问题

### 为什么刚才还正常，突然列表里几十个节点同一秒全部变成 Timeout？

极少出现几十台不同地区的服务器在同一秒全部物理宕机的情况。全量同时超时最常见于三个原因：一是本地电脑/手机自身时间漂移或宽带断网；二是客户端测试延迟的 URL 被干扰导致全员“假超时”；三是机场中转入口统一变更或整套账户/节点池被下线。

### 测速显示全部 Timeout，但偶尔还能打开外网是怎么回事？

这是典型的“测速接口失效引起的假超时”。部分客户端默认使用 Google generate_204 作为延迟探测地址，若探测逻辑设置异常、节点未正确响应或本地测速并发过高被限流，测速界面会显示 Timeout，但实际转发流量仍可用。

### 全节点超时和套餐过期或流量用完有关系吗？

有直接关系。许多机场在用户流量耗尽或套餐到期后，不会主动删除客户端里的旧节点，而是直接在服务端吊销对应 UUID/密码，导致客户端连接任意节点都会瞬间断开或持续超时。
