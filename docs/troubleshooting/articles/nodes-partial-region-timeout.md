# 仅单个节点或特定地区超时排查：节点维护、路由劣化与测速 0B 解读

## 核心结论（Answer-First）

仅单个节点或特定地区超时而其他地区正常，说明你的本地网络、客户端核心与账户额度均正常。结合 `2026-08-11` 等真实批次测速记录可见，单点出现 `0B` 或几 `KB` 低速多源于**单机临时重启维护、入口端口更换未刷新订阅、单地区跨境上游劣化，或旧内核不支持特定新协议（如 Hysteria2/AnyTLS）**。刷新订阅并启用 `url-test`/`fallback` 自动切换即可规避。

## 故障现象

- **客户端测速局部红字分化**：香港、新加坡分组真连接延迟稳定在 `45ms–110ms`，但日本分组整片红字 `Timeout`，或者同一个地区里“香港 01 / 03 / 04”全绿，唯独你平时手动选定的“香港 02”单独显示 `-1` 或 `Timeout`。
- **实测图中的 `0B` 与个位数 `KB` 异常点**：在第三方自动化测速图（如 `MAI-TEST-BOT` / `Miaoko`）或本地批量测速表中，同批几十个节点大多拥有数十 `MB/s` 的正常峰值，唯独某一行刺眼地标着 `0B`（如 `2026-08-11` 实测快照中多个品牌曾分别出现过 `香港 02 = 0B`、`香港 01 = 0B`、`台湾 02 = 0B`），或者个别节点卡在 `8KB`、`12KB`、`17.59KB` 极微弱速率。
- **核心日志特征**：当代理策略硬编码锁死在该异常节点时，日志反复刷出指向单一目标的 `dial tcp <特定入口IP:端口>: i/o timeout` 或 `read: connection reset by peer`；一旦手动切到旁边编号节点，日志立刻恢复正常转发。

## 先做 3 个低风险检查

1. **立刻做同地区不同编号与跨地区横向切换**：排障第一铁律是**不要死磕单一报错节点**。如果 `香港 02` 超时，花 3 秒点选 `香港 04` 或 `新加坡 01` 测试网页能否秒开——只要换一个节点立刻恢复，就无需去折腾本机系统网卡、DNS 或重装软件。
2. **手动点击一次“更新订阅”**：机场日常运维经常会下线被打瘫的旧中转 IP、更换单台机器端口或调整节点编号。如果你半个月没点更新订阅，客户端拿着早已作废的旧端口去敲门，自然只有这几个变更过的节点报超时。
3. **核对异常节点的协议标签与倍率备注**：仔细看一眼报错节点的名字里是否带有特殊后缀——比如 `HY2`（Hysteria2）、`TUIC`、`AnyTLS`、`IPv6 Only`、`0.1x 下载专用` 或 `游戏 UDP`。很多时候并不是“某个地区坏了”，而是“那几个节点恰好用了你当前老旧客户端不认识的新协议，或者用了被你家宽带阻断的纯 UDP 协议”。

## 读懂实测记录：单点 `0B`、残余 `KB` 低速、单区劣化与节点下线的本质区别

不少用户在看评测实测图（可参阅 [品牌深度评测总目录](/reviews/) 中的原始测速档案）或自己跑测速时，一看到列表里出现 `0B` 就误以为“这家机场快跑路了”，或者反过来面对整区瘫痪好几天还以为是自己电脑坏了。结合 `2026-07` 至 `2026-08-11` 多份真实测速样本，我们可以按以下四维矩阵精准定性：

| 观察到的测速 / 延迟现象 | 底层网络状态还原 | 典型真实案例形态 | 属于单点偶发、区域劣化还是下线警报？ |
| :--- | :--- | :--- | :--- |
| **单个节点 `0B` 且无延迟（同组其余节点正常）** | 该节点入口 TCP/TLS 未建立，或中转至落地隧道中断，转发有效载荷为 0 字节 | 如 `2026-08-11` 批次实测中，部分平时吞吐正常的品牌同批节点跑出几十 MB/s，唯独单个 `香港 02` 或 `香港 01` 记录为 `0B` | **单节点偶发维护 / 故障**。多为单机重启、单入口更换或瞬时被墙，切同区其他节点即可，完全不影响整体使用 |
| **有毫秒级延迟，但测速仅有 `8KB`–`20KB`（KB 级爬行）** | 握手与鉴权已通！但数据传输阶段遭遇严厉队列限速、跨网严重丢包导致 TCP 拥塞窗口缩死，或落地机 CPU/连接表耗尽 | 如历史实测快照中曾出现的个别 `日本 05 = 8KB`、某日本节点 `12KB` 或某狮城节点 `17.59KB` | **单节点过载或限流劣化**。常见于低倍率福利节点被挂 BT/视频挤爆，有 Ping 却打不开视频，需手动避开这类“假绿残血节点” |
| **某单一国家/地区全灭（如日本全红，港新全绿）** | 该地区共用的国内专线入口、海底光缆（如中日方向 IIJ/SoftBank 链路）或同一家上游落地机房出现集体故障 | 晚高峰特定运营商到某单线中转入口跨网拥堵，或东京/洛杉矶某单一机房遭 DDoS 清洗黑洞 | **单区链路劣化 / 机房波动**。通常在数小时至 1–2 天内由运维切换入口恢复，期间改用相邻地区（如港/新/台互备） |
| **全地区 90% 以上节点连续多日 `0B` + 官网失联** | 全部中转入口欠费停机或后端鉴权数据库关闭 | 刷新订阅报 `502/404`，切换移动 5G 热点后全节点依旧死寂 | **全局停摆 / 疑似跑路信号**！此时不再是局部故障，应立即转入全局排障与止损流程 |

## 分层原因排除

### 本地系统与网络

- **本地宽带运营商与单入口“跨网水土不服”**：同一家机场里，香港组可能走广深移动入口，而日本组走上海电信或联通入口。如果你家里装的是移动宽带，晚高峰跨网访问电信入口且该机场未做三网 BGP 接入时，就会表现为只有对应地区的节点大量丢包超时。
- **纯 IPv6 入口节点与本地纯 IPv4 环境错配**：部分机场会放几条标注 `IPv6` 的直连备用节点，若你的家庭路由器未开启 IPv6 或处于内网 NAT 后，点选这几条节点必定 100% 超时。

### 客户端与核心配置

- **老旧客户端内核对混合订阅中的新协议“偏科”**：当下不少机场在一个订阅里混合下发传统 `Shadowsocks / Trojan`（占 70%）与新锐 `VLESS-Reality / Hysteria2 / AnyTLS`（占 30%）。如果用户还在用停更的老内核，就会出现前 70% 节点全通、后 30% 新协议节点全部超时或直接被丢弃的现象。
- **UDP 协议节点遭遇本地防火墙或运营商阻断**：当超时节点清一色属于基于 UDP 的 Hysteria2 / TUIC，而同地区的 TCP 节点完全正常时，根因在于本地网络阻断了大流量 UDP（详见 [UDP 转发失败与防火墙阻断排查](/troubleshooting/articles/udp-nat-firewall-blocks)）。
- **策略组写死在单一编号节点上（缺乏自动容灾）**：很多新手习惯在 `PROXY` 主策略组里手动点选“香港 01”就再也不管了。一旦两周后“香港 01”例行重启维护 20 分钟，明明列表里还有 15 个完好的香港节点，用户的网络却立刻瘫痪。

### DNS 与路由分流

- **单节点入口 CNAME 刚切换但本地缓存未过期**：运维在后台通过 DNS 把故障入口 `hk02.example.invalid` 切到了备用机 IP，但用户本地路由器把 TTL 强行延长缓存了旧坏 IP，导致别人已恢复而你还在连死 IP。
- **落地机屏蔽了客户端默认测速探针 URL**：极个别严格策略的海外落地机房拦截了对 `www.gstatic.com/generate_204` 或特定测速大文件的请求，造成客户端面板显示 `Timeout` 或 `0B`，但实际挂上它刷网页完全正常。

### 远端订阅与节点

- **单机流量耗尽、端口被封或高热门节点挤兑**：标注“家宽原生”、“AI 专用”或“0.1 倍率”的节点往往承载了远超普通节点的并发请求，高峰期新建连接极易排队超时。

## 操作路径

### 步骤 1：更新订阅并核对客户端内核对故障节点协议的支持度

1. **桌面端（Clash Verge Rev / FlClash / v2rayN）**：
   - 先点击更新订阅并清理一次系统 DNS 缓存（Windows 执行 `Clear-DnsClientCache`），排除旧端口与旧解析缓存。
   - 右键查看超时节点的具体协议类型（`type`）：若包含 `vless`（`flow: xtls-rprx-vision` / `reality-opts`）、`hysteria2`、`tuic` 或 `anytls`，请确保 Clash Verge Rev 运行在最新版 Mihomo 内核，v2rayN 已补齐最新 `xray` 与 `sing-box` 双核心（详见 [v2rayN 核心无法加载与更新修复](/troubleshooting/articles/v2rayn-core-load-fail)）。
2. **iOS（Shadowrocket）与 Android（v2rayNG / Clash Meta）**：
   - 在节点详情查看传输协议，确保客户端来自官方最新维护版本（勿使用已停更数年的旧版 CFA）。
3. **OpenWrt（OpenClash / PassWall2 / HomeProxy）**：
   - 检查软路由插件状态页是否已编译包含对应协议组件（如 PassWall 单独勾选安装 `sing-box` 或 `hysteria` 组件包）。

### 步骤 2：在终端对“正常节点 vs 超时节点”做入口连通性对比测试

无需暴露任何密码或 UUID，仅对比正常节点与故障节点的入口地址与端口（以下使用占位域名 `node-hk01.example.invalid` 与 `node-hk02.example.invalid`，自测时替换为客户端节点详情中的服务器地址与端口）：

**命令 A：Windows PowerShell 对照检测 DNS 解析与 TCP 端口握手**

- **适用 OS**：Windows 10 / Windows 11
- **目的**：分清故障节点到底是域名没解析出 IP、入口 TCP 端口彻底不通，还是 TCP 通但上层协议挂死。
- **风险等级**：低风险（只读三次握手测试，不发送代理载荷）。
- **预期输出解读**：
  - 若 `hk01` 的 `TcpTestSucceeded` 为 `True`，而 `hk02` 为 `False`，100% 证实你家宽带到 `hk02` 这台入口机的传输层已断开（机器停机、端口关闭或入口 IP 被封），直接放弃该单节点换用 `hk01` 即可；
  - 若 `hk02` 也是 `True` 但真连接测速为 `-1`（或该节点是 UDP 协议），说明入口机器活着，故障在于中转后端断连、UDP 被阻断或协议参数不兼容。

```powershell
Resolve-DnsName -Name "node-hk02.example.invalid" -Type A
Test-NetConnection -ComputerName "node-hk01.example.invalid" -Port 443 | Select-Object ComputerName, RemoteAddress, TcpTestSucceeded
Test-NetConnection -ComputerName "node-hk02.example.invalid" -Port 443 | Select-Object ComputerName, RemoteAddress, TcpTestSucceeded
```

**命令 B：macOS / Linux / OpenWrt 使用 `nc` 快速对比端口响应**

- **适用 OS**：macOS、Linux、OpenWrt（SSH 终端）
- **目的**：3 秒限时探测故障节点入口端口是否开放。
- **风险等级**：低风险（只读探测）。
- **预期输出解读**：返回 `succeeded!` / `open` 代表入口 TCP 通畅；返回 `Operation timed out` 或 `Connection refused` 代表远端单点入口离线或端口已关闭。

```bash
nc -zv -w 3 node-hk02.example.invalid 443
```

### 步骤 3：配置 `fallback` / `url-test` 自动容灾策略组，告别单节点断网

为防止日后某台节点半夜维护（变成 `0B`）把你的主力网络挂断，强烈建议不要把总开关长期钉死在某一个单节点名字上，而是在客户端策略组选用或通过局部 Merge 覆写建立**自动故障转移组**：

```yaml
# 在 Clash Verge Rev / Mihomo 的 Merge 扩展中示例说明策略组容灾参数原理
proxy-groups:
  - name: "香港自动容灾"
    type: fallback
    url: "https://www.gstatic.com/generate_204"
    interval: 300
    lazy: true
    include-all: true
    filter: "(?i)港|HK|Hong Kong"
```

- **`fallback`（故障转移）与 `url-test`（自动选最低延迟）怎么选？**
  - 如果你对 IP 频繁跳变敏感（例如使用 AI 对话工具或登录风控较严的后台，不希望每 5 分钟因为延迟波动 10ms 就换一个出口 IP），优先使用 **`fallback`**——只要排第一位的节点没挂（非 `0B`/超时），它就一直稳稳固定不跳；一旦第一台节点维护超时，自动顺延切到第二台。
  - 如果纯粹看视频、下资料追求最快响应，选择机场自带的 **`url-test`（自动选择）** 分组即可。

## 什么结果算修复

- 切换到同地区正常编号节点或启用 `fallback`/`url-test` 自动分组后，业务连接立即恢复，不再因单个节点 `0B` 维护而断流。
- 若此前因内核过旧导致 Hysteria2 / Reality 节点成片超时，更新维护版客户端后该批节点恢复真实毫秒级延迟与吞吐。
- 在客户端日志中不再持续刷出指向已废弃单节点的连接超时重试错误。

## 若仍失败怎么办

1. **排查晚高峰周期性区域拥塞**：如果日本或美国分组白天飞快、一到晚上 20:00–23:30 就准时掉到几 `KB` 或超时，这属于典型的跨网或共享带宽晚高峰拥堵，请阅读 [晚高峰高延迟、丢包与卡顿定位](/troubleshooting/articles/high-latency-packet-loss-peak)。
2. **仅个别网站打不开而非节点真超时**：如果节点测速全绿，只有 ChatGPT、Claude 或 Netflix 报错不可用，请转入 [仅个别网站或 AI 工具打不开排查](/troubleshooting/articles/specific-sites-unreachable)。
3. **从局部超时恶化为全线失联**：若原本只是日本挂了，随后香港、新加坡、美国陆续全部变为 `Timeout` 且官网无法打开，请立即对照 [所有节点同时超时排查](/troubleshooting/articles/nodes-all-timeout) 与 [机场跑路识别与止损步骤](/security/shutdown/) 核查服务商运营状况，并可在 [香港节点专线解析](/routes/hong-kong/)、[日本节点路由分析](/routes/japan/) 与 [深度评测目录](/reviews/) 中了解不同线路架构的抗风险差异。

## 高风险操作与回滚提示

- **严禁关闭杀毒软件或重置本机全部网络栈来“抢修单个远端坏节点”**：95% 的单节点超时与单点 `0B` 发生在百公里外的机场中转机或海外机房，折腾本地注册表和防火墙百害而无一利。
- **严禁在群聊或论坛直接截图暴露节点的真实入口域名/IP 与密码**：公开节点入口只会招致恶意扫描加速该入口被封禁，提问时仅需说明地区编号与协议类型。
- **自定义策略组 Merge 覆写的回滚**：若添加正则筛选策略组（如 `filter: "HK"`）时因机场命名不含对应关键词导致组内节点为空而报错，在 Clash Verge Rev「订阅」页直接关闭该 Merge 扩展开关并重载配置，即可立即回退到机场默认分组。

## 常见问题

### 测速表或实测截图里某一个节点显示 0B 或 Timeout，代表整个机场都不能用了吗？

不代表。正如 2026-08-11 等多批次实测档案中反复观察到的那样，即使整体吞吐良好的服务商，也常在某一时刻出现单个节点如“香港 02 = 0B”或个别节点仅几 KB/s，而同批次其他节点跑满数十 MB/s 的分化现象。这通常只是单台落地实例重启维护、单入口更换端口或瞬时并发打满，切换到同地区相邻编号节点即可立刻恢复。

### 为什么只挂了“美国节点”或只挂了“日本节点”，香港和新加坡却完全正常？

同一地区的节点往往共用一条上游跨境出口或同一家落地机房供应商。当某条跨境海缆抖动、某地区落地机房被批量拔线或遭遇 DDoS 清洗时，就会出现按地区成片超时而其他地区不受影响的现象。

### 同一个香港组里 1 号节点正常、3 号节点超时，是我本地网络的问题吗？

大概率不是本地网络故障，而是远端 3 号节点自身离线、更换了端口尚未同步，或你本地网络到该节点特定中转 IP 的路由存在高丢包。先更新一次订阅，若仍超时直接避开该节点即可。

### 节点测速只跑出几 KB/s（如 8KB、12KB）和彻底 0B 有什么区别？

彻底 0B（伴随 Timeout）通常意味着 TCP/TLS 握手阶段就已失败、入站端口已关闭或远端转发进程挂死；而有合法延迟但吞吐仅有 8KB–20KB/s，说明握手和鉴权本身是通的，但该节点正遭受严厉的机房带宽限流、晚高峰高丢包引发 TCP 窗口坍缩，或者落地出口对测速文件服务器触发了速率限制。
