# 晚高峰高延迟、丢包与卡顿定位：本地宽带、中转与落地瓶颈区分

## 核心结论（Answer-First）

晚高峰（20:00–23:00）代理延迟飙升与卡顿，本质上是“**本地宽带与 Wi-Fi**”“**国内中转/跨境入口**”“**远端落地服务器**”三段链路之一出现拥塞或丢包。通过“本地网关直连对比 -> 同机场多入口节点横向测试 -> 代理端口 TTFB 首包检测”三步分段测量，5 分钟内即可分清是自家网络问题还是节点超售拥堵。

## 故障现象

- **典型时间规律**：工作日下午或凌晨速度正常，一到每晚 20:00–23:00 或周末晚间，视频自动降到 360p/480p，图片加载残缺，AI 对话输出卡住或直接断流。
- **桌面端与移动端共性表现**：客户端内的节点测速延迟从平时的 `40ms` 跳升至 `300ms–1200ms`，甚至间隔出现 `Timeout`；部分用户即使看到绿色低延迟数字，浏览器左下角仍长期停留在 `正在建立安全连接...` 或 `Waiting for...`。
- **与测速记录的体感落差**：参考白天非晚高峰测试截图（例如单次静态测速结果）入手的服务，实际晚间并发环境下带宽大幅缩水甚至频繁断流，这正是“非高峰样本无法代表全天稳定性”的典型表现。

## 先做 3 个低风险检查

1. **检查局域网是否有设备正在抢占上行/下行带宽**：查看家里是否有人正在用网盘上传备份、主机更新大型游戏、电视盒看高码率直播或 BT 下载。家用宽带上行带宽极窄（常见仅 30–50Mbps），一旦上行打满，所有下行网页与代理 ACK 确认包都会剧烈延迟和丢包。
2. **临时从 2.4GHz Wi-Fi 切到 5GHz 或网线直连**：2.4GHz 频段在晚间邻居路由器全开时同频干扰极严重，自身就能造成 10% 以上的无线丢包。
3. **测试“关掉代理访问国内大站”是否同样变慢**：先关闭客户端系统代理/TUN，打开国内主流门户或视频站；如果连国内直连都在卡顿掉帧，问题根源就在本地路由器、光猫过热或运营商片区宽带故障。

## 分层原因排除

### 本地系统与网络

- **本地 Wi-Fi 信道拥挤与光猫性能瓶颈**：百元级光猫长时间开启路由模式且 NAT 会话数过多时，晚间全家设备同时联网会出现 CPU 满载与丢包。
- **跨网 QOS 与本地上行拥塞**：部分地区宽带（尤其部分二级宽带或共享小区宽带）在晚高峰本身存在国际方向及跨网 QOS 限速。

### 客户端与核心配置

- **使用了不适合当前网络环境的并发/多路复用配置**：在丢包率本就不低的晚高峰，如果手动开启了激进的 `mux` 多路复用（把多条连接塞进同一条 TCP 隧道），一旦底层出现单个丢包，就会触发全局队头阻塞（Head-of-Line Blocking），导致所有网页同时卡死。
- **系统代理与网页多连接限制或 TUN 网卡队列溢出**：低配置软路由或老旧设备开 TUN 模式转发大流量时，单核转发达到上限同样会表现为“网速上不去且延迟剧烈抖动”。

### DNS 与路由分流

- **DNS 解析绕远或频繁超时**：在高峰期，若代理配置里填写的 `nameserver` 或 `fallback` 公共 DoH 服务器本身响应变慢（例如动辄 800ms 才返回结果），网页打开前就会白白卡在域名解析阶段，让人误以为“节点速度慢”。
- **CDN 调度失真与“送中”回流**：例如访问 YouTube 或大型图床时，由于节点或 DNS 归属识别偏差导致流量被调度到高负载节点甚至误回流（参见 [YouTube 加速与送中排查](/ai-media/youtube/)），体感会明显变慢。

### 远端订阅与节点

- **公网直连与普通 BGP 中转的晚高峰跨境拥塞**：无专线保障的普通公网节点在晚间国际出口极其拥挤，丢包率可能飙升至 10% 以上。
- **单节点共享超售与落地机性能枯竭**：即便是声称带有中转或专线的线路，如果服务商在同一个落地 VPS 上塞入过多用户，晚高峰时段落地机 CPU、磁盘 IO 或出口带宽一样会被打满。

## 操作路径

### 适用平台说明

- **适用平台**：Windows、macOS、Linux、OpenWrt（完整覆盖本地网关延迟、路由跟踪与代理端口首包检测）；iOS 与 Android 适用核心排查思路（Wi-Fi/5G 切换、多地区节点对照、关闭激进多路复用），终端抓包/路由跟踪命令则在桌面端或路由器上执行。

### 分段排查与诊断命令

1. **步骤 1：验证本地路由器与国内公网基础丢包率（关闭代理）**
   - **适用 OS**：Windows（PowerShell / CMD）
   - **目的**：向本地网关和国内高可用公共地址发送连续探测包，区分丢包是发生在家中内网还是出境之后。
   - **风险等级**：低（只读 ICMP 探测，不改动任何系统配置）。

   ```powershell
   # 先测试本地默认网关（请将 192.168.1.1 替换为你实际的路由器网关 IP）
   ping -n 20 192.168.1.1
   # 再测试国内骨干公网节点丢包情况
   ping -n 20 223.5.5.5
   ```

   - **预期输出解读**：
     - 如果连 `192.168.1.1` 都出现 `请求超时` 或延迟超过 `20ms` 剧烈波动，100% 是家中 Wi-Fi 干扰、网线接触不良或路由器过热死机。
     - 如果网关稳定 `<2ms` 且 `223.5.5.5` 丢包为 `0%`、延迟稳定，说明本地内网与国内直连正常，拥塞点大概率在跨境链路或节点侧。

2. **步骤 2：在 macOS / Linux / OpenWrt 排查分跳丢包与延迟突增位置（关闭代理）**
   - **适用 OS**：macOS / Linux / OpenWrt
   - **目的**：观测数据包离开本地宽带、经过省网/骨干网出口的延迟跳变点（若已知目标服务或直连测试点）。
   - **风险等级**：低（只读路由路径探测）。

   ```bash
   # Linux/OpenWrt 若已安装 mtr 可运行 20 轮快速汇总；macOS 可用 traceroute -n
   traceroute -n -q 3 223.5.5.5
   ```

   - **预期输出解读**：
     - 第 1 跳（本地网关）和第 2–3 跳（运营商汇聚网段）延迟正常应在 `1ms–15ms` 之间。如果第 2 跳（运营商接入网）就出现 `100ms+` 或星号 `* * *` 连续丢包，说明当地小区宽带本身处于严重拥塞中。

3. **步骤 3：测量代理端口下的真实握手与首包响应耗时（开启代理）**
   - **适用 OS**：Windows / macOS / Linux（需先确认本地代理端口，常见 Clash 系为 `7890`，v2rayN 默认为 `10808` SOCKS / `10809` HTTP，请以客户端界面实际显示为准）
   - **目的**：跳过客户端列表“虚假 ICMP/TCP Ping”，直接观测从代理隧道发起完整 TLS 连接到收到服务端首字节响应（TTFB）的真实耗时。
   - **风险等级**：低（只读访问常见连通性检测页，不改动设置）。

   ```bash
   # 将 127.0.0.1:7890 替换为你客户端实际监听的 HTTP 代理端口
   curl -x http://127.0.0.1:7890 -o /dev/null -s -w "DNS:%{time_namelookup}s Connect:%{time_connect}s TLS:%{time_appconnect}s TTFB:%{time_starttransfer}s Total:%{time_total}s\n" https://www.gstatic.com/generate_204
   ```

   - **预期输出解读**：
     - 若 `TLS` 耗时（`time_appconnect` 减去 `time_connect`）超过 `1.5s` 甚至超时，说明本地到节点入口之间握手丢包严重或被阻塞。
     - 若 `TLS` 很快但 `TTFB`（`time_starttransfer`）显著偏大，通常是远端节点到目标站之间拥塞或落地机负载极高。

4. **步骤 4：执行多入口/冷门节点横向切换与单双栈对照**
   - 在客户端把节点从热门“香港 01”切到同机场的“日本/新加坡/台湾”或标注了不同中转线路（如联通/电信/移动优化入口）的节点，重新运行步骤 3 的 `curl` 对比 `TLS` 与 `TTFB` 数据；若某个特定入口表现大幅改善，即证实原节点属于单线拥塞。
   - 同步在手机端切换 **5G 移动数据** 与 **家庭 Wi-Fi** 对比同一节点的表现，以排除单一家庭宽带运营商的跨网晚高峰限速。

## 什么结果算修复

- 在晚高峰时段（20:00–23:00）连续执行上述 `curl` 首包测试 5 次，全部成功返回，且 `TLS` 与 `TTFB` 波动稳定（例如亚洲近距离节点维持在 `0.2s–0.6s` 区间内，无单次飙升至 `3s+` 或超时）。
- 连续 Ping 本地网关 20 次丢包率为 `0%`，排除家中无线干扰。
- 打开目标网页或 1080p 流媒体能顺畅起播且无反复缓冲降画质。

## 若仍失败怎么办

- 检查是否使用了超低价或单月超售严重的线路，参考 [稳定机场标准与专线核验](/airport/stable/) 与 [IEPL/IPLC 专线原理与辨别](/routes/iepl/) 了解不同线路等级的抗拥塞边界。
- 如果本地宽带运营商在晚间严格限速国际/特定中转入口（移动/电信/联通三网表现差异极大），可优先准备一家主用 + 一家不同骨干入口的备用方案做容灾，参见 [品牌替代方案矩阵](/brands/alternatives/)。
- 如果仅在播放游戏或语音时丢包卡顿，需进一步排查是否受到 UDP 限速影响，参阅 [UDP 转发失败与防火墙限制排查](/troubleshooting/articles/udp-nat-firewall-blocks)。

## 高风险操作与回滚提示

- **修改路由器 QoS、信道带宽或光猫桥接前务必记录原参数**：调整路由器无线信道或关闭硬件加速前，先截图当前无线/WAN 配置；OpenWrt 修改 `/etc/config/network` 或 `/etc/config/wireless` 前先执行 `cp /etc/config/wireless /etc/config/wireless.bak`，若导致设备连不上 Wi-Fi，可通过网线连接或回写备份文件后执行 `wifi reload` 回滚。
- **切勿盲目在系统注册表或内核参数中刷入来历不明的“TCP 拥塞加速脚本/BBR 魔改一键包”**：桌面系统篡改 `netsh int tcp` 高级参数或 Linux 随意替换内核可能引起本地网卡蓝屏、系统更新失败或本地直连异常；若已改动 Windows TCP 参数，可通过管理员 PowerShell 执行 `netsh int tcp reset` 并重启电脑恢复系统默认栈。

## 常见问题

### 为什么白天或者看到别人发的非晚高峰测速截图很快，一到晚上八点半就卡得打不开网页？

绝大多数普通公网直连或共享带宽中转线路在每天 20:00–23:00 都会遭遇家用宽带国际出口拥塞与用户并发峰值。一份在白天（如上午或下午非高峰时段）测得的测速图只能证明当时环境下到达过的峰值速率，不能直接推导出晚高峰同样流畅；遇到晚高峰卡顿时需重新测试真实晚高峰表现。

### 客户端测延迟只有 40ms，为什么打开网页还是卡顿转圈好几秒？

客户端列表里显示的“延迟”往往只是客户端到中转入口（或单次 TCP/HTTP 探测）的瞬时 RTT，不代表高并发下的丢包率与落地服务器真实负载。只要链路后半段（中转到落地机，或落地机到目标网站）存在 5%–15% 丢包或 CPU 跑满，TCP 重传就会让实际网页首屏卡顿数秒。

### 晚高峰卡顿时应该换“低倍率节点”还是“冷门地区节点”？

若核心瓶颈在于大家同时挤在热门香港/新加坡低倍率节点导致落地机拥塞，临时切到日本、台湾、美国等负载相对更低的冷门节点（或明确走独立中转入口的备用线路）通常能立刻缓解；但如果连同一家机场的国内中转入口都全线丢包，则需要检查本地宽带或切换多备用线路。
